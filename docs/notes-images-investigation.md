# Notes images investigation (F-S107)

Investigation baseline: InvenTree **1.7.4 / API 570**, selected by the operator on 2026-11-28. This is a feasibility report, not authorization to add tools. No notes-image client methods, MCP tools, deployment, or new implementation issue are introduced.

## Evidence and reproduction

The checked API 570 schema exposes only GET/POST `/api/note/image/`. `NotesImage` contains `pk`, `image`, `user`, `date`, and required `note`. The `image` URI response schema does not describe a working JSON upload. Both qualified and short model-type filters are characterized. The `note` FK filter validates note existence: querying a deleted note returns 400, so cascade absence is checked through its surviving parent filter and the stored file response. The existing endpoint manifest continues to exclude this surface from runtime tools.

## Upload and representation

The web client sends multipart `image` bytes and a stable `note` ID. The serializer supplies creator/date; the storage backend returns `image`, typically `/media/notes/<filename>`. A missing/deleted note or invalid raster is rejected. Storage basename handling and collision renaming are not content deduplication: repeating identical bytes/name creates another row and another storage URL. Do not blindly retry an ambiguous POST.

`InvenTreeImageSerializerField` inherits DRF/Pillow validation; it has no note-specific byte, dimension, or MIME allowlist in the tagged source. Actual decoder availability and reverse-proxy/Django settings affect accepted inputs and limits. PNG success and malformed/SVG rejection are characterized; this does not establish exhaustive upstream media support or a safe size ceiling. A future MCP contract must impose its own bounded raster policy rather than infer one from the URI schema.

Upload does **not** modify the note content, primary flag, or note update timestamp. Embedding requires a second PATCH of the note. The 1.7.4 web editor loads sanitized HTML into TipTap and saves sanitized `editor.getHTML()`. Its resizable-image extension inserts an HTML image using the returned URL. The server's `nh3` sanitizer preserves approved `<img src="/media/notes/..." alt="...">` HTML. Bare `![alt](url)` survives as text; source inspection shows no Markdown conversion in this editor. API retention of Markdown does not prove a rendered image. Existing MCP notes accept text, but their historical “Markdown” wording should not be interpreted as a guarantee that Markdown images render in 1.7.4. No browser-rendering test is claimed here.

## Permissions and media boundary

Image metadata listing filters by the requesting user's **parent model view permission**, using the note relation. Upload checks parent **change permission**, rather than creator identity. The live part case distinguishes an empty list and denied upload with no role, successful listing but denied upload with view-only permission, and successful upload by another user with change permission. Successful upload/list/HTML association/note deletion is characterized for the six supported notes types: parts, companies, supplier parts, manufacturer parts, stock items, and purchase orders. Granular single-role separation for the other five types is source-verified, not independently isolated.

Templates are visible through the upstream queryset and need staff rights for writes. They remain excluded from the proposed MCP surface, as do all other model types. A future tool must resolve a supported, readable note and readable live parent before metadata, upload, or download; a raw note/image ID or a successful media GET is insufficient authorization. Filter `note` is useful scoping, not proof the note is readable or exists: denied scopes can return an empty list, while a deleted note ID is rejected with 400. Do not expose the upstream unscoped list or arbitrary creator/domain filters.

**Direct media access is a separate boundary.** The disposable stack characterizes unauthenticated denial and authenticated byte access by a user who cannot list the owning note's images. Source middleware checks authentication, not the owning note's model role, for these media paths. Production reverse proxies/storage can differ and need their own verification. Never claim parent permissions protect a disclosed raw media URL. A future MCP download must independently preflight note/parent permission and select the URL from that note's scoped metadata using the same credential; it cannot repair a URL already shared outside MCP. Existing `get_note`/search results can already contain media URLs inside note content, so withholding raw links from future download results does not make those existing URLs private.

## Lifecycle and failure recovery

- Each note save invokes `cleanup_images`: linked images whose storage URL is absent from the resulting content are deleted **immediately**, including on metadata-only or primary-selection updates. This is substring matching, not parsed image-reference checking. Keeping a URL in Markdown text retains the row without proving the browser displays it.
- Uploads not yet embedded survive until another save or scheduled cleanup. An unrelated title/description/primary change between upload and embedding can delete the upload. A future combined workflow needs before/after reads and explicit single-writer guidance; a plan hash is not an upstream lock or compare-and-swap.
- Replacement means upload a fresh image, PATCH content while preserving wanted references, then verify the new row and content. Removing the old URL deletes its row/file during the PATCH. There is no exposed image detail, PATCH, or DELETE endpoint, and no in-place replacement API. Do not add private/admin/database fallbacks.
- A failed PATCH after a successful upload leaves an unembedded image. On a known failed PATCH, re-read content and scoped images and report the uploaded image ID plus whether it remains. On an ambiguous upload/PATCH, re-read before deciding to retry; list metadata alone cannot prove identical bytes or intent. Do not automatically delete the note or perform a metadata-only “cleanup” save: that can delete other pending uploads.
- The image belongs to one note. Referencing its URL in another note does not change ownership; removing the original reference or deleting its owner can break the second note. Cross-note reuse should be excluded; upload independent copies instead. This is inferred from the FK/cleanup implementation, not a live cross-note rendering test.
- Deleting the note cascades image rows; a post-delete signal schedules storage deletion after commit. The live suite verifies rows disappear and stored bytes return 404. Parent deletion invokes the upstream notes cleanup path; that cascade and transaction-rollback semantics have source/upstream-test evidence, not an independent MCP fixture test here. Storage backend deletion failures remain possible.
- The daily scheduled task removes missing-file records regardless of age and images at least roughly 90 days old when their URL is absent from their owning note. It does not provide a 90-day recovery guarantee: any note save can delete an unreferenced image earlier. Scheduled aging is source-verified, not a live 90-day wait or clock-modified database test.

The legacy common.0051 migration creates notes from old model `notes`, links directly attached or content-referenced images, preserves directly attached images on blank notes via an empty primary note, and removes still-unlinked rows. Matching is URL-based, and an unlinked image is claimed by one note. common.0052 removes old model association columns and makes the note FK mandatory. These are historical source findings; a fresh 1.7.4 container is not proof of preservation when upgrading a populated old database. Backup and independently validate a real legacy migration before making that claim. Upstream `copy_notes_from` copies bytes and rewrites references for new notes; a future MCP workflow must not infer that generic string copying does the same.

## Proposed bounded implementation contract (not approved)

Defer implementation until the operator chooses how to handle the media-permission limitation and approves the two-write recovery semantics. No new task ID/issue is reserved by this report. If approved, a separate implementation task should cover these acceptance criteria:

1. Scoped image metadata/list and bounded download by stable `note_id` plus image ID; require `inventree.read`, supported note/parent checks, bounded pagination, no expanded user records, no arbitrary URL input. Fetch only the URL actually returned for the selected image belonging to that note, on the configured instance and media path. Bound reads; reject unsafe redirects, credentials and unexpected content; redact URLs and bytes from logs/errors. Return inline image bytes only through the normal image result contract, not reusable unguarded links.
2. A guarded upload-and-embed operation for an existing note, with explicit append/replace intent, sanitized/escaped HTML image construction, preview/confirm plan, parent, full content-state and scoped image-ID/URL-set binding, pre-write revalidation and post-write verification. Refuse any pre-existing or unexpected unreferenced uploads before a content PATCH, including append-only operations: upload alone does not advance the note timestamp, and a save could otherwise delete another writer's pending image. This preflight still has a race; require single-writer use. Read+write+upload scopes are additive. Because content replacement can remove image references and delete files, explicitly classify replacement/removal under destructive authorization; do not silently treat it as a harmless upload. Do not offer arbitrary image-row DELETE or implicit note creation/primary selection. Account for image cleanup in existing note updates before adding an upload tool.
3. Reuse `internal/upload` inline resolution and STDIO allowlisted direct-Afero local reads; never accept local paths in HTTP mode. Apply the existing raster-validation policy (PNG/JPEG/WebP, 5 MiB encoded, 4096 per dimension, 16 million pixels, validated complete decoding and MIME/extension agreement) through a suitably named shared validator. Reject SVG and other formats unless separately reviewed. Keep URL ingestion out of the first scope; a later dedicated URL tool would need SSRF-safe DNS/dial/redirect handling and no forwarded auth headers.
4. Reuse `internal/render` to generate PNG server-side and pass it directly to the same guarded embed workflow. Do not relay large base64 blobs through the model or route through generic attachments/part primary-image assignment. Rendering is deterministic; attachment and content mutation still need confirmation, scopes and recovery outcomes.
5. Return distinct outcomes for uploaded-but-not-embedded, outcome-unknown, vanished upload, verified embedded, and failed verification. Return safe stable IDs and recovery instructions, never a claim of atomicity or automatic rollback. No durable exactly-once guarantee is available from this upstream API.
6. Cover all six domains, role boundaries, scoped-download denial despite broad media access, malformed/oversized/unsupported images, same-instance URL/redirect checks, duplicate and lost-response handling, concurrent note edits, metadata/primary cleanup, reference removal, cross-note restrictions, and delete cascades with deterministic unit tests and isolated real API tests. Run full race suite, per-package coverage comparison and Go/QA/product/infosec review before marking that task Done.

### Bulk assessment

Independent existing notes could eventually use the shared bounded batch executor, each item owning upload + content PATCH + verification with per-item partial outcomes. Preflight all items and reject repeated note IDs; preserve each note's complete content and references. Multiple uploads into the same note are dependent and must be one ordered workflow item with a single final content update, not parallel independent batch rows: an intervening PATCH can delete the other uploads. Cross-item rollback is unavailable. Defer public bulk upload until the single-note recovery contract is approved and tested; this is an ordering/partial-failure boundary rather than a reason to invent an upstream atomic batch endpoint.

## Decisions required before implementation

- Accept upstream authenticated media access being broader than parent-note metadata permissions, with MCP preflight and explicit deployment guidance, or require an upstream/proxy fix before shipping any notes-image capability?
- Approve a guarded two-write HTML embed workflow with explicit partial/unknown outcomes and single-writer use, or keep image authoring in the InvenTree web editor?
- Approve explicit replacement/removal and its destructive authorization requirements, or start with append-only embedding and scoped reads? Existing note updates can already trigger cleanup; this must be reflected in the implementation safety review.

These are future product decisions, not assumptions this investigation implements. Production reverse-proxy media authorization, browser visual rendering, legacy populated upgrades, exhaustive decoder limits and granular roles for five model types remain validation limits. The current recommendation is to defer new tools until the decisions above are made.
