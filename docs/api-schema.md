## Verified Auth and Token Endpoints

These are InvenTree upstream authentication endpoints and schemes. They are not the MCP server's HTTP OAuth endpoints.

The MCP server's ChatGPT-facing OAuth issuer is separate from these InvenTree endpoints. Do not point ChatGPT directly at InvenTree `/o/authorize/` or `/o/token/` unless the product plan is explicitly changed.

Security schemes:

- `tokenAuth` uses `Authorization: Token <token>`.
- The schema also describes OAuth2 endpoints with `authorizationUrl: /o/authorize/`, `tokenUrl: /o/token/`, and `refreshUrl: /o/revoke_token/`.

Current-user validation endpoints:

- `GET /api/user/me/` retrieves the authenticated user's record and is suitable as a cheap credential validity check.
- `GET /api/user/me/roles/` retrieves the authenticated user's roles and is also suitable as a cheap credential validity check.

Current-user API token endpoints:

- `GET /api/user/me/token/?name=<name>` is schema-confirmed for token issuance/lookup behavior, but implementation must verify whether the response includes a usable secret only at creation time. Do not rely on any InvenTree endpoint to recover an already-created token secret.
- `GET /api/user/tokens/` lists current-user API tokens.
- `POST /api/user/tokens/` creates a current-user API token.
- `GET /api/user/tokens/{id}/` retrieves current-user API token metadata.
- `DELETE /api/user/tokens/{id}/` revokes or deletes a current-user API token.

F-S08 uses `GET /api/user/me/` to bind setup to the authenticated InvenTree user and `GET /api/user/me/token/?name=inventree-mcp-chatgpt-<random-setup-id>` to create a uniquely named dedicated connector token without rotating the supplied credential or an earlier connector token. Default-on Testcontainers coverage verifies that the endpoint returns a one-time usable token secret on the pinned InvenTree baseline. Abandoned or expired authorizations can leave unused dedicated tokens that the operator must revoke through InvenTree's token management UI/API. If token creation is unavailable, setup discards the submitted secret and requires explicit operator consent before sealing a re-entered supplied credential.

HTTP MCP connector auth mapping:

- STDIO mode may use configured `Token` or `Bearer` upstream credentials directly.
- HTTP mode should not pass raw InvenTree `Authorization` headers through unchanged. The MCP server should validate its own OAuth access-token envelope, recover the sealed upstream credential, and then call InvenTree using `Authorization: Token ...` or `Authorization: Bearer ...`.

## Verified Parameter Template Endpoints

- `GET /api/parameter/template/` searches parameter templates.
- `POST /api/parameter/template/` creates a template from the `ParameterTemplate` schema.
- `GET /api/parameter/template/{id}/` reads one template.
- `PATCH /api/parameter/template/{id}/` preserves omitted fields through `PatchedParameterTemplate`, including explicit empty/false values and explicit null selection-list removal.
- `DELETE /api/parameter/template/{id}/` deletes one template only after tool-layer reference preflight.
- `GET /api/parameter/` with exact `template` scans template references across model types. Template administration bounds this scan to 1,000 rows and fails closed above that limit.
- `GET /api/part/category/parameters/` supplies category-default reference preflight. Because the pinned API does not filter this endpoint by template, F-S11 scans at most 1,000 links, fails closed if completeness cannot be established, and leaves mutation to the category-default administration story.

The tool layer refuses direct deletion while any parameter row or category-default link remains. Template merge migrates only non-conflicting `part.part` rows, preserves unmapped values, normalizes only explicit `value_map` entries, and refreshes both reference sets immediately before deleting an empty source. These REST operations are not atomic; operators must prevent concurrent template/reference administration because a narrow reference-creation race remains between final preflight and delete.

## Verified Attachment Endpoints

- `GET /api/attachment/` lists attachments.
- `POST /api/attachment/` creates attachments and supports `multipart/form-data`.
- `DELETE /api/attachment/` performs bulk delete.
- `GET /api/attachment/{id}/` retrieves attachment metadata.
- `PUT /api/attachment/{id}/` updates attachment data.
- `PATCH /api/attachment/{id}/` partially updates attachment data.
- `DELETE /api/attachment/{id}/` deletes one attachment.

Useful list filters:

- `model_type`
- `model_id`
- `is_file`
- `is_image`
- `is_link`
- `has_thumbnail`
- `tags`
- `upload_user`
- `search`
- `limit`
- `offset`

Attachment fields include:

- `attachment`
- `thumbnail`
- `filename`
- `link`
- `comment`
- `is_image`
- `upload_date`
- `upload_user`
- `file_size`

- `model_type`
- `model_id`
- `tags`

Attachment content download is not a separate schema endpoint in the current schema snapshot. Implement `download_attachment` by resolving metadata first, rejecting out-of-scope attachment `model_type` values, then fetching the schema-exposed `attachment` URL by default or `thumbnail` URL in explicit thumbnail mode through the InvenTree client, scoped to the configured InvenTree base URL and authenticated as the current InvenTree user. Do not treat arbitrary user-provided URLs or stored link targets as downloadable attachment content.

Workflow mapping:

- `upload_attachment` posts a file attachment using the `attachment` field and never accepts HTTP(S) URLs.
- `download_attachment` reads an existing file attachment using the metadata `attachment` field by default, or `thumbnail` field in explicit thumbnail mode, and returns bounded content to the caller.
- `download_part_image` reads a part's primary image by resolving only that part's readable schema-exposed `image` field or the part thumbnail endpoint and returns bounded content to the caller. It does not accept arbitrary URLs and does not require the operator to know a generic attachment ID.
- `upload_attachment_from_url` fetches remote bytes under the server's URL-fetch policy, then posts a file attachment using the `attachment` field.
- `create_link_attachment` stores a URL in the `link` field without fetching the URL.

Attachment model types in the schema include:

- `build`
- `company`
- `manufacturerpart`
- `supplierpart`
- `purchaseorder`
- `returnorder`
- `salesorder`
- `salesordershipment`
- `transferorder`
- `part`
- `stockitem`

Initial implementation should expose only non-sales model types relevant to the current product scope.

The attachment endpoint's `AttachmentModelTypeEnum` uses short, unqualified values such as `part`, `stockitem`, and `purchaseorder`. This is distinct from the parameter endpoint's `ModelTypeD42Enum`, which uses qualified Django-style `app.model` values such as `part.part`, `stock.stocklocation`, and `order.purchaseorder`. MCP tools preserve both schema-defined vocabularies: attachment tools accept only the in-scope short values, while parameter-template administration accepts the qualified values or an explicit empty unrestricted value. Neither vocabulary is an alias for the other.

## Verified Image Fields

- `Part` exposes readable `image` and write-only `existing_image`.
- `Company` exposes `image`.
- Generic attachments expose `is_image`, `thumbnail`, and `file_size`.
- `/api/part/thumbs/` and `/api/part/thumbs/{id}/` expose part thumbnail listing and update behavior using `PartThumb` and `PartThumbSerializerUpdate`.
- `/api/notes-image-upload/` exposes note image upload behavior, which is separate from inventory object attachments.

Primary-image behavior must be implemented per object type from schema-verified fields rather than assumed generically.
Part primary image download is part-specific for the first release. It should use the part record's readable `image` value or the part thumbnail endpoint, scope the fetch to the configured InvenTree base URL, authenticate as the current InvenTree user, and apply the same maximum-size and redaction controls as attachment downloads. `existing_image` is write-only and is only valid as assignment/update input.
Part primary image assignment uses multipart `PATCH /api/part/{id}/` with the `image` file field after the tool resolves and downloads an existing same-part image attachment. Pinned InvenTree 1.5.0/API 530 integration rejects using a generic attachment URL with `PATCH /api/part/thumbs/{id}/`; that endpoint remains verified for thumbnail retrieval/update schema behavior, while the tool contract keeps assignment behind `set_primary_image`. `existing_image` is write-only and is not used as a download source or caller-facing shortcut.
Company primary-image assignment uses multipart `PATCH /api/company/{id}/` with the `image` file field. Pinned InvenTree 1.5.0/API 530 validation proves that first assignment stores the original bytes, replacement returns a distinct collision-safe image URL and removes the prior media file, and JSON `image:null` clears the exact company association and removes the current media file. F-S31 verifies assignment and replacement by downloading only the resulting same-instance schema-exposed URL and comparing its SHA-256 digest with the submitted bytes; clear requires confirmed exact-null read-back. These operations preserve all company roles and unrelated detail fields and are distinct from generic company attachments.
Notes image upload, generated report attachments, stock test-result attachments, and other app-specific file surfaces are out of first-release scope unless a later task explicitly adds them.

- Company search/get/create/update and role filters, plus supplier-part and manufacturer-part link search/get/create/update dependencies implemented by F-S20. Company tags remain excluded from the current public projection despite becoming schema-visible because F-S61 does not expand tool behavior. The manufacturer-part schema requires `part` and `manufacturer` but declares `MPN` nullable and optional. Pinned InvenTree 1.5.0 nevertheless rejects POST creation when `MPN` is omitted; F-S15 preserves the schema-facing optional input by omitting null, blank, and whitespace-only values, returning bounded validation from the direct create tool, and making the combined workflow reuse one exact part/manufacturer link, clarify multiple links, or skip creation when none exists rather than inventing a value. The supplier list schema supports the generic `company` filter, `manufacturer_part` reverse-link filter, and `SKU` ordering; the manufacturer list supports `manufacturer` filtering and `MPN` ordering. Role-removal postflight uses the generic supplier `company` filter and a bounded unfiltered manufacturer snapshot because the role-specific filters are rejected after the corresponding role is removed. Because neither ordering enum exposes the stable primary key, F-S20 fetches one complete snapshot of at most 1,000 matching rows and performs stable-ID sorting locally rather than offset-scanning an unstable ordering. Public tools expose only approved patch fields; F-S39 validates complete credential-free HTTP(S) links, preserves query and fragment components in successful exact projections, and keeps recovery projections URL-free instead of mirroring every writable serializer field.
- Stock location search/get/create/PATCH, location-type search/get references, stock item search/get/create/constrained PATCH, and native add, remove, count, transfer, and status-change operations. ## Verified Part Detail And Scalar Maintenance

- `search_parts` keeps the concise selection projection. `GET /api/part/{id}/` backs the complete approved scalar `get_part` projection and exact create/update read-back.
- `internal/inventree.PartFieldInventory` classifies every pinned API 530 `Part` property. Scalar identity, category/default IDs, flags, image/thumbnail, IPN/revision/units/notes, creation metadata, pricing bounds, nullable stock/allocation aggregates, and `revision_of` / `revision_count` / `variant_of` family fields are exposed. Nested category/default-location detail, category path, and parameters are separate lookups. Tags, price breaks, and ownership remain deferred; write-only duplication/initialization/image inputs remain unavailable; raw `barcode_hash` is excluded.
- `creation_user` is read-only at the MCP boundary even though the upstream serializer does not mark it read-only. Part primary-image mutation remains in the dedicated image tools.
- POST/PATCH scalar inputs preserve omission versus explicit false/zero. Nullable keywords, link, revision, and notes use explicit clear flags at the tool boundary and JSON null upstream. `default_expiry:0` resets expiry; `maximum_stock:0` disables the maximum. Minimum/maximum stock must be finite and non-negative, and a nonzero effective maximum cannot be below the effective minimum.
- Part external links use the F-S39 complete credential-free HTTP(S) policy. Invalid or credential-bearing stored values are omitted from successful tool output, and rejected input values are not echoed in errors or recovery projections.
- `create_part` and `update_part` require `inventree.read` plus `inventree.write`, remain closed-world and non-destructive, retain `idempotentHint:false`, and read back the exact stable record. If an acknowledged mutation cannot be read back, the tool returns `partial_failure` with a PK-only `recovery` identity when the mutation response supplied a positive stable ID; the complete `record` remains omitted. If creation supplied no usable ID, both `record` and `recovery` are omitted and the recovery plan directs exact search and reconciliation before retry.
- API 530 exposes nullable writable `revision_of` and `variant_of` stable IDs, nullable read-only `revision_count`, and server-side `revision_of` / `variant_of` list filters. Pinned InvenTree 1.5.0 additionally requires a nonblank revision code when `revision_of` is set, rejects template parts as revision targets, requires the part and revision target to point to the same variant template, and only accepts template parts as `variant_of` targets, but it accepts the tested circular `revision_of` chain. `update_part_family_relationships` is the only MCP mutation surface for these topology fields and therefore supplies the required bounded cycle guard; it also rejects direct self-reference as an explicit safety policy. It requires an exact current-state dry run and a principal-bound five-minute single-use token, binds both current references, requested targets, relevant eligibility state, and deterministic traversal evidence, and fails closed after a shared 64-record exact-read budget. Every call uses read, write, operational, and destructive scopes with `destructiveHint:true`; ordinary `update_part` remains scalar-only. Successful or ambiguous PATCH results require exact stable-ID read-back, and recovery projections contain only family IDs rather than unrelated part data.

## Verified Related-Part Administration Endpoints

## Verified Stock Adjustment Endpoints

- `POST /api/stock/add/` adds a positive relative quantity to one or more stock items through `StockAdd`.
- `POST /api/stock/remove/` removes a positive relative quantity through `StockRemove`.
- `POST /api/stock/count/` records an absolute stocktake quantity through `StockCount`. The schema permits optional location and per-item metadata changes, but F-S05 intentionally sends only one item ID, absolute quantity, and audit notes so stocktake remains quantity-only.
- `POST /api/stock/change_status/` changes stock status through `StockChangeStatus` and records the operator reason as the transaction note.
- `POST /api/stock/transfer/` accepts `StockTransfer` with an `items` array of stock-item IDs and decimal quantities, transaction `notes`, and one destination `location`. F-S27 intentionally sends exactly one item with its complete reviewed current quantity and an explicit destination. Pinned InvenTree 1.5.0 verification confirms a full transfer preserves the original stable stock-item ID, quantity, batch, packaging, status, supplier/purchase provenance, and price/currency while adding an exact-item tracking entry containing the audit reason.
- F-S05 exposes only single-item operations. Every tool reads current state, produces a state-bound dry-run plan, returns an opaque principal-bound five-minute single-use confirmation token in `plan_hash`, requires that token with `confirm:true` and a nonblank audit reason, then reads back the stock item. Quantity decreases and `Destroyed` (`60`), `Rejected` (`65`), or `Lost` (`70`) statuses are flagged as high-risk.
- The stock adjustment tools are operational, closed-world, non-destructive, and require `inventree.read`, `inventree.write`, and `inventree.operational`. They refuse no-op changes, quantity changes to serialized stock, and zeroing a `delete_on_deplete` item; serialized status-only changes remain supported. Ambiguous mutation results, including HTTP `408`, `425`, and `429`, are not retried automatically.
- F-S51 adds the separate destructive `set_stock_delete_on_deplete` workflow on the native `PATCH /api/stock/<id>/` endpoint already used by `update_stock_item_metadata`. It plans and confirms only the `delete_on_deplete` boolean; every other field, and the quantity itself, is left unchanged. Enabling the flag is high-risk because it authorizes InvenTree to delete the stock-item record the next time a depletion transaction (native or through `deplete_stock_item`) reduces its quantity to zero; disabling it revokes that authorization. The tool itself never removes stock or changes quantity, so it is valid at any current quantity including zero, and requires `inventree.read`, `inventree.write`, `inventree.operational`, and `inventree.destructive`. No-op requests (the item already has the requested policy) are refused before a plan is issued. Pinned InvenTree 1.5.0 integration verification found the global `STOCK_DELETE_ON_DEPLETE` server setting defaults to enabled, so a stock item created through `create_stock_item`/`create_initial_stock_entry` without this tool already carries `delete_on_deplete:true` unless the deployment's global setting was changed; operators who want a receiving placeholder to survive depletion must explicitly disable the policy with this tool.
- F-S24 adds the separate destructive `deplete_stock_item` workflow on the same native `POST /api/stock/remove/` endpoint. It removes the complete current positive quantity only when `delete_on_deplete:true` and the exact stock item is in stock, unallocated, non-serialized, not building or consumed, not installed, and has no parent, child, or installed-item relationship. The high-risk dry run binds safe stock, allocation, relationship, and supplier/order/build provenance fields into a principal-bound confirmation token. Execution records the audit reason and treats exact-ID `404` after removal—including after an ambiguous response—as verified deletion.
- F-S27 adds the operational `transfer_stock_item` workflow. It requires one exact stock-item ID with a current source location, one explicit exact destination-location ID, a nonblank reason, a reviewed plan, and `inventree.read`, `inventree.write`, plus `inventree.operational`. The MCP does not exclude structural, external, owned, or typed destinations during preflight; every exact-read destination is passed to native InvenTree validation, while same-location requests are refused as no-ops. Source stock must be available, positive, unallocated, unserialized, and free of build, consumption, installation, customer/sales, and parent/child relationships. The schema's `tracking_items` value is an audit-event count rather than a child-stock relationship, so it remains visible through stock reads but does not block transfer or enter the current-state verification fingerprint. The tool has no quantity input and reports `will_split:false`. F-S28 owns partial/split behavior and F-S29 owns multi-item batches.
- InvenTree exposes no conditional stock mutation or revision value across these endpoints. Concurrent adjustment of the same stock item by any writer is unsupported: execution rejects state changes observed during its preflight, while a change in the subsequent read/write window can still race and is reported as `partial_failure` when readback diverges.
- F-S53 adds `update_stock_item_provenance` on the native `PATCH /api/stock/{id}/` endpoint. It is separate from the constrained metadata PATCH and permits only supplier-part, purchase-order, purchase-price, and purchase-price-currency corrections after exact current-state planning. The supplier part must belong to the stock item's base part; when both references are present, their suppliers must match, and the plan token binds the validated supplier/order identities and suppliers as well as the complete stock state. The opaque confirmation token is principal-bound, five-minute, and single-use. Explicit null clears are accepted only for fields the pinned serializer declares nullable; `purchase_price_currency` is non-nullable and cannot be cleared. The workflow is destructive, non-idempotent, requires all four inventory scopes, and verifies the complete stock state after mutation. The generic PATCH does not create a stock-tracking event, so the correction changes current provenance without rewriting historical tracking entries; operators must retain the reviewed correction context externally.

## Verified Part Deletion And Guard-Only Reads

`DELETE /api/part/{id}/` is far more permissive than its blast radius suggests. Pinned live behavior against InvenTree 1.5.0 (`TestClientMethodsAgainstInvenTree/part_delete`), isolating one reference category per part rather than combining several:

- InvenTree itself enforces exactly two conditions: the part must be **inactive** first (`non_field_errors: ["Cannot delete this part as it is still active"]`), and a part currently used as a **component in another part's BOM** is protected (`non_field_errors: ["Cannot delete this part as it is used in an assembly"]`).
- Every other reference this schema exposes is **silently permitted** once the part is inactive, and the consequence differs by relation: deleting a part with an existing stock item also **destroys that stock item** (not merely orphans it); a referencing purchase-order line **survives, orphaned**; a part's own BOM (as assembly), a build where it is the top-level part, a sales-order line, a variant (`variant_of`), a supplier part, a manufacturer part, a parameter, an attachment, and a related-part link are all permitted with no independently verified child-record fate beyond "the part itself deletes."
- `delete_part` therefore treats every one of these categories as blocking in its own preflight rather than relying on any upstream protection or cascade.

Four resources had no Go client plumbing before `delete_part` needed them for read-only existence checks. BOM, sales-order-line, and build reads remain guard-only; F-S42 now promotes related-part reads and administration to dedicated MCP tools:

- `GET /api/bom/` -- `part` filters a part's own BOM (as assembly); `uses` filters where a part is consumed as a component elsewhere (including template/variant expansion; exact semantics pinned by the integration test rather than assumed).
- `GET /api/order/so-line/` -- `part` is the direct `Part.PK` (unlike `/api/order/po-line/`, where the response's `part` field is actually the supplier-part PK; `delete_part` uses the dedicated `base_part` filter to query the base `Part.PK` directly instead of fanning out over supplier parts).
- `GET /api/build/` -- `part` filters builds where the part is the top-level built part.
- `GET /api/part/related/` -- `part` matches a relation where the part is on *either* side (`part_1` or `part_2`), pinned by deliberately placing the tested part as `part_2` in the integration test rather than assuming symmetry. F-S42 additionally exposes exact GET plus guarded POST, note-only PATCH, and DELETE as documented above.
- `GET /api/part/?variant_of=<id>` finds parts that are variants of a given template part; deleting a template with existing variants is blocked.

## Verified Instance Info Endpoints

F-S71's `get_inventree_instance_info` is the first `inventree.read` tool that reads staff-scoped InvenTree administrative data (global settings) rather than ordinary business data. Its acceptance criteria required a BLOCKING GATE: the concrete global-settings allowlist below was drafted by starting a pinned InvenTree 1.5.0 Testcontainers instance and inspecting the actual live value of every one of the 158 global settings and 42 user settings it returned, not just their names or schema descriptions, and was explicitly approved by the operator on 2026-08-16 before any tool code was written. Endpoints used:

- `GET /api/` (`root_retrieve`, `#/components/schemas/InfoApi`) supplies `server`, `version`, `apiVersion`, `instance`, and `plugins_enabled`. Its schema description notes "some information might be blanked if called without elevated credentials," so no special error handling is applied for reduced-privilege responses; other `InfoApi` fields (`platform`, `database`, `django_admin`, `installer`, `docker_mode`, `debug_mode`, `worker_*`, `active_plugins`, `email_configured`, the `customize`/`settings` sub-objects, `system_health`, `target`, `id`) are deliberately not exposed, either because they reveal operational/fingerprinting detail (OS/arch, DB engine, admin URL path, installed-plugin versions) or because they duplicate the excluded auth-policy settings below.

This endpoint declares OAuth security scope `a:staff` (unlike `/api/`'s `g:read`), so a `403` here is treated as omittable: the tool simply leaves `commit_hash`/`commit_date`/`up_to_date` out of its response rather than failing the call. The response's `version.django` and `version.python` fields are excluded (dependency-CVE fingerprinting risk).
- `GET /api/settings/global/{key}/` (`settings_global_retrieve`, `#/components/schemas/GlobalSettings`) fetches only the 23 allowlisted keys below, one request per key -- never the list endpoint, and never filtered client-side. Its schema description states "User must have 'staff' status to view / edit" even though its declared OAuth scope is only `g:read`; a resulting `403`, or a `404` for a renamed/removed key, is treated as omittable and reported by key in the tool's `omitted_global_settings` output rather than failing the call.
- `GET /api/settings/user/{key}/` (`settings_user_retrieve`, `#/components/schemas/UserSettings`) fetches only the one allowlisted key below for the caller's own settings, with the same graceful `omitted_user_settings` degradation.

Schema/runtime mismatch discovered during the live-instance review: `docs/api-schema.yaml` declares `GlobalSettings.value` and `UserSettings.value` as `type: string`, but the live InvenTree 1.5.0 API returns boolean- and integer-typed settings as native JSON scalars (for example `{"value": false}`, not `{"value": "false"}`). `internal/inventree.GetGlobalSetting`/`GetUserSetting` decode into `json.RawMessage` and normalize to a display string rather than assuming the schema's declared string type; a JSON string value is unquoted, and any other scalar (bool, number, `null`) is rendered as its raw JSON text.

## Verified Stock Tracking And Stocktake Endpoints

- `GET /api/stock/track/` (`stock_track_list`, `#/components/schemas/PaginatedStockTrackingList`) lists `StockItemTracking` audit events. `list_stock_tracking_entries` requires an exact `stock_item_id` or `part_id` and always passes it server-side as the schema's `item` or `part` filter; it never scans the endpoint unfiltered. `item_detail`/`user_detail` default to `false` upstream and are left at that default, so the top-level response carries only stable `item`/`part`/`user` IDs, never embedded nested records.
- `GET /api/stock/track/{id}/` (`stock_track_retrieve`, `#/components/schemas/StockTracking`) backs `get_stock_tracking_entry`, an exact single-event read.
- The schema declares `StockTracking.deltas` with no `type`, i.e. genuinely untyped per-event JSON. A pinned 2026-08-18 spike against InvenTree 1.5.0/API 530 (see `docs/TASKS.md`'s F-S46 Decisions for the full write-up) triggered create/add/remove/count/transfer/status-change/PO-receipt events and found the key set and value shapes vary by `tracking_type`, and that at least two event types (`Location changed`, `Received against Purchase Order`) unconditionally embed a full nested `*_detail` record inside `deltas` -- independent of the top-level `item_detail`/`user_detail`/`part_detail` query flags -- including a `purchaseorder_detail.created_by` object carrying a real user's email and username.
- `internal/inventree.SanitizeStockTrackingDeltas` therefore treats `deltas` as a bounded, redacted opaque JSON object rather than an explicit per-event typed union (a typed union was rejected because future stories such as F-S52/F-S54/F-S66 will add InvenTree-side event types this repository does not control). It recursively strips any object key ending in `_detail` and the known non-suffixed `created_by` nested-user convention (retaining the sibling stable-ID key, e.g. `location` or `purchaseorder`, that always accompanies the stripped key), then rejects -- rather than truncates -- any redacted payload that still exceeds a fixed maximum nesting depth, maximum total key count, or maximum serialized byte size, or that contains a JSON value type outside object/array/string/number/bool/null.
- This is a denylist of known InvenTree nested-record conventions, not an allowlist of approved `deltas` keys, chosen deliberately over a stricter allowlist so that legitimate-but-unanticipated audit fields (new scalar keys a future InvenTree release adds to an existing event type) remain visible rather than silently dropped. The tradeoff is accepted per the 2026-08-18 post-implementation Infosec review: the denylist is proven exhaustive against every nested-user/owner embedding in the pinned typed OpenAPI schema (all follow either the `_detail` suffix or the bare `created_by` convention), but `deltas` itself is genuinely untyped, so this guarantee does not formally extend to an undiscovered future event type that might embed a nested record under some other key name. As a second, defense-in-depth layer independent of key naming, `internal/inventree.looksLikeIdentityRecord` also strips any nested object whose own keys include `email` or `username` (case-insensitive), regardless of the enclosing key's name -- this specifically narrows, but does not eliminate, the residual gap for a hypothetical future event embedding some other PII shape (for example a phone number or physical address) under a key this check does not recognize. Re-run the pinned deltas-shape spike against any new event type introduced by a future story (F-S52/F-S54/F-S65/F-S66) before publishing its schema.
- `list_stock_tracking_entries` sorts by stable event `pk` (never upstream `date`, which is not guaranteed unique or stable-ordered across same-instant events) before paginating, and its concise projection omits the free-text `notes` field; `get_stock_tracking_entry` includes `notes`.
- `GET /api/part/stocktake/` (`part_stocktake_list`, `#/components/schemas/PaginatedPartStocktakeList`) and `GET /api/part/stocktake/{id}/` (`part_stocktake_retrieve`) back `list_part_stocktakes` (which requires an exact `part` filter and sorts by stable `pk` before paginating) and `get_part_stocktake`. Both are read-only: `POST`/`PUT`/`PATCH`/`DELETE /api/part/stocktake/` and `POST /api/part/stocktake/generate/` are intentionally never called. Pinned InvenTree source restricts the detail endpoint (`retrieve`/`update`/`partial_update`/`destroy`) to staff/admin accounts; a non-staff InvenTree credential therefore receives a `403` from `get_part_stocktake`, which the tool surfaces as an ordinary upstream error rather than a special case.
- Pinned live-instance discovery (2026-08-18): `POST /api/part/stocktake/` fails with a `500` on every request regardless of payload on InvenTree 1.5.0 -- its view unconditionally passes an unsupported `user` keyword to the `PartStocktake` model constructor, which this version's schema declares no `user` field for (`TypeError: PartStocktake() got unexpected keyword arguments: 'user'`). `POST /api/part/stocktake/generate/` returns `200` immediately but only enqueues generation on InvenTree's background-worker task queue; this repository's Testcontainers suite intentionally runs only the InvenTree web process (see `internal/testenv`), so a generated snapshot never actually appears. Both findings reinforce (independent of the read-only tool-surface decision already made) that this story's live coverage cannot populate a real stocktake snapshot; see `docs/TASKS.md`'s F-S46 Residual risk.
- Stocktake records expose `date`, `item_count`, `quantity`, `cost_min`/`cost_min_currency`, and `cost_max`/`cost_max_currency`; nested `part_detail` remains a separate `get_part` lookup.

Explicitly considered and excluded from instance identity: `active_plugins` (the full installed-plugin roster including version numbers -- real fingerprinting/attack-surface intelligence) and the general `/api/plugins/` surface (a separate, larger, security-sensitive endpoint family with install/activate/uninstall operations nearby). The operator asked whether broader plugin visibility was needed for a possible future stocktake-related story; the resolution was to keep only `plugins_enabled` plus the two low-risk feature-selection keys above, and to defer any deeper plugin-status need (for example, whether a specific report-generating plugin is active) to that future story's own scoped investigation rather than exposing the general plugin roster here.

## Verified Contact And Address Endpoints

- `GET /api/company/contact/` (`company_contact_list`, `#/components/schemas/PaginatedContactList`) and `GET /api/company/contact/{id}/` (`company_contact_retrieve`, `#/components/schemas/Contact`) back `search_contacts` and `get_contact`. `search_contacts` always sends the schema's `company` filter server-side (`company_id` is a required tool input, not optional narrowing) so the tool can never return contacts outside the requested company; `search` narrows by upstream `name`/`company__name` text search. `POST`/`PATCH`/`DELETE /api/company/contact/` are intentionally never called by any tool per the F-S49 operator decision; Testcontainers fixtures create contact records directly through the InvenTree API for test setup only.
- `GET /api/company/address/` (`company_address_list`, `#/components/schemas/PaginatedAddressList`) and `GET /api/company/address/{id}/` (`company_address_retrieve`, `#/components/schemas/Address`) back `search_addresses` and `get_address` with the same required-`company_id`, never-broader-than-requested-company contract. `POST`/`PATCH`/`DELETE /api/company/address/` are likewise never called by any tool.
- `internal/inventree.ContactFieldInventory` and `internal/inventree.AddressFieldInventory` classify every pinned `Contact`/`Address` serializer property as exposed or excluded, backed by raw-key contract tests against `docs/api-schema.yaml` (mirroring `CompanyFieldInventory`/`PurchaseOrderFieldInventory`'s drift protection). Per the F-S49 operator decision, `Contact.phone`/`Contact.email` and `Address.line1`/`Address.line2`/`Address.postal_code` are excluded from both search and exact-read projections -- not just from search disambiguation candidates -- so contact/address PII never reaches agent context; the Go `Contact`/`Address` types have no field at all for the excluded properties, so `json.Unmarshal` silently drops them and they never reappear on re-marshal. `Address.link` is additionally passed through the F-S39 credential-rejecting external-URL policy (`AddressView` in `internal/tools/address_tools.go`) the same way every other MCP-projected URL field is, since `Contact`/`Address` records are as untrusted as any other upstream data even though most of their fields are excluded outright.
- `PurchaseOrder.contact`/`PurchaseOrder.address` flip from `PurchaseOrderFieldDeferred` to `PurchaseOrderFieldExposed` in `PurchaseOrderFieldInventory`; `contact_detail`/`address_detail` flip from `PurchaseOrderFieldDeferred` to `PurchaseOrderFieldSeparateLookup`, matching the existing `responsible`/`responsible_detail` precedent -- the nullable stable ID is exposed on `get_purchase_order`, while the nested embedded record is never returned and must be looked up separately through `get_contact`/`get_address`.

## Verified Stock Location Detail And Type Administration Endpoints

- `GET /api/stock/location/{id}/` (`stock_location_retrieve`, `#/components/schemas/Location`) already requests `path_detail=true`. `Location.icon` is a read-only, non-nullable field the InvenTree serializer computes server-side -- its schema description states "The icon field on this model takes precedences over the possibly assigned stock location type" -- so `get_stock_location`/`search_stock_locations` expose it directly as the effective icon alongside the separately writable, nullable `custom_icon`; no client-side fallback computation is needed or performed. `internal/inventree.StockLocationFieldInventory` classifies every pinned `Location` serializer property (19 total): `barcode_hash` stays excluded pending F-S55, `tags`/`parameters` stay deferred to F-S56/F-S64, `location_type_detail` is classified `exposed` rather than `separate_lookup` because the existing `get_stock_location`/`search_stock_locations` projection already carries it (predating this story) and every other field is exposed, backed by a raw-key contract test against `docs/api-schema.yaml`.
- `internal/inventree.StockLocationTypeFieldInventory` classifies every pinned `StockLocationType` serializer property (`pk`, `name`, `description`, `icon`, `location_count`) as exposed; the type is a small flat reference record with no deferred or nested content.
- `POST /api/stock/location-type/` (`stock_location_type_create`), `PATCH /api/stock/location-type/{id}/` (`stock_location_type_partial_update`), and `DELETE /api/stock/location-type/{id}/` (`stock_location_type_destroy`) back `create_stock_location_type`, `update_stock_location_type`, and `delete_stock_location_type`. Unlike `Category.icon`/`Category.default_keywords` (nullable, cleared via `PATCH {field: null}`), `StockLocationType.name`/`description`/`icon` are all non-nullable optional strings (`maxLength`, "may be blank" -- never `nullable: true`); an explicit clear is therefore expressed as `PATCH {field: ""}` (`inventree.Set("")`), never a null-clear, and there is no separate `clear_x` boolean input for this tool.
- Pinned live discovery against InvenTree 1.5.0 (`TestClientMethodsAgainstInvenTree/stock_location_type_administration`, 2026-08-19): the API does **not** enforce name uniqueness on `StockLocationType` -- creating two types with the identical name both succeed with `201`. `create_stock_location_type`/`update_stock_location_type` therefore perform their own bounded case-insensitive duplicate-name preflight (paginated over `GET /api/stock/location-type/`, capped at 1,000 records, failing closed past that bound) as the sole uniqueness guard; this is load-bearing MCP-side behavior, not a redundant safety net over an upstream constraint.
- Pinned live discovery, same test: deleting a `StockLocationType` that is still referenced by one or more locations succeeds with `204` and safely `SET NULL`s `location_type` (and consequently the effective `icon`, which falls back to none) on every referencing location, rather than refusing the delete or cascading further. `delete_stock_location_type` therefore does not block on existing references; instead its guarded plan token binds both the exact current type record and a bounded complete snapshot of every referencing location's stable ID (scanned via the existing `GET /api/stock/location/?location_type=<id>` filter, capped at 1,000 records, failing closed past that bound), so the operator reviews the reported `referencing_location_ids` before confirming, and any reference-set change between preview and confirm makes the token stale rather than silently deleting against unreviewed state. Execution re-reads the type by its exact stable ID after the delete attempt and reports `verified:true` only once a `404` proves absence.
- Reads require `inventree.read`; `create_stock_location_type`/`update_stock_location_type` require `inventree.read` plus `inventree.write` and remain non-destructive; `delete_stock_location_type` additionally requires `inventree.destructive` and publishes `destructiveHint:true`.
- `assign_contact` and `assign_address` PATCH the same `PATCH /api/order/po/{id}/` endpoint `update_purchase_order` already uses (no new manifest entry), setting or `null`-clearing only the `contact`/`address` field via `UpdatePurchaseOrderDetail`. Among already-supported objects, API 530 exposes structured `contact`/`address` FK references only on `PurchaseOrder` (`ReturnOrder`, `SalesOrder`, and `TransferOrder` carry the same fields but remain unimplemented/sales-adjacent), so both tools take `purchase_order_id` directly rather than F-S48's `object_type`/`object_id` matrix shape. Before issuing a plan, the resolved target's `company` field is checked against the order's `supplier`; a mismatch is rejected as `validation_failed` without ever issuing a plan token. Each tool's plan token binds the order ID, the order's current supplier `company_id`, and the order's current `contact`/`address` value, so either the supplier or the reference changing between preview and confirm changes the recomputed plan digest and makes the token stale -- the same current-state-binding mechanism `assign_owner` established, extended with the additional company-context field this story's acceptance criteria require. Discovery reads require `inventree.read`; `assign_contact`/`assign_address` require `inventree.read`, `inventree.write`, and `inventree.destructive`, publish `destructiveHint:true`, and remain closed-world and non-idempotent.
