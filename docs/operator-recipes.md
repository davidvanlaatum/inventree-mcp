# Operator Recipes

This file is the source of truth for first-release operator workflows. README should link here instead of duplicating full recipes.

Each recipe should preserve omitted fields versus explicit zero/false/empty values, prefer existing InvenTree records, and return a structured clarification instead of guessing when lookup results are ambiguous.

## Local CLI Self-Update

This recipe applies only to a binary installed directly from a GitHub release archive on supported Linux or macOS `amd64`/`arm64` systems. It is a local CLI operation, not an MCP workflow.

1. Confirm the binary did not come from `deb`, `rpm`, `apk`, Homebrew, or another package manager. Package-managed `/usr/bin/inventree-mcp` must be upgraded with the package manager.
2. Confirm `inventree-mcp version` reports an exact stable `vX.Y.Z` release. Development builds cannot self-update.
3. Before the first update only, run `inventree-mcp self-update --adopt-direct-install`. This creates an owner-only marker bound to the canonical repository and executable path without contacting GitHub or changing the binary. Never adopt a package-managed or uncertain installation.
4. Run `inventree-mcp self-update` for the latest stable release, or `inventree-mcp self-update --version vX.Y.Z` for an exact newer stable release.
5. On success, run `inventree-mcp version` and retain `<installed-path>.previous` until the new binary has completed the operator's normal smoke test.
6. On refusal, follow the reported package-manager/manual-upgrade guidance. Do not use `sudo` to bypass ownership, directory, symlink, hardlink, marker, platform, or package boundaries.

The updater verifies the canonical GitHub archive against `checksums.txt`, sanitizes the staged version probe, uses a persistent owner-only kernel-locked lock file and durable transaction record, rolls back failed installed probes, and never sends InvenTree/MCP credentials. It deliberately rejects the multi-file `v0.0.1` archive; the next single-binary release is the first valid target.

`inventree-mcp version` prints human-readable text by default; `inventree-mcp version --porcelain <N>` prints a versioned, key-based porcelain format (`porcelain: 1` plus `version`/`commit`/`date` and, when available, `inventree_version`/`inventree_api`) for porcelain format version `N`. Self-update always requests the format version it understands from the staged candidate. This replaced a fixed 3-line default output as a one-time breaking change: any binary from `v0.0.1`-`v0.0.11`, or any later release before the change shipped, invokes bare `version` when probing a candidate and cannot parse the new human-readable default response — it reports "malformed version output" and refuses to self-update into the first release carrying this change. Download and install that specific release manually (see README's [Install From A Release](../README.md#install-from-a-release) section), then run `inventree-mcp version` to confirm the new format; every release after it self-updates normally. See [Local CLI self-update policy](self-update.md) for the full format and migration details.

If the command reports that it recovered an interrupted self-update, that invocation has restored the pre-update executable and exited non-zero without selecting or downloading a release. Run `inventree-mcp version`, inspect the restored version, then rerun the original `self-update` command so release selection uses that restored executable. Cleanup-only records left after a completed install or rollback are removed automatically without changing the current executable.

If the later smoke test requires manual recovery, stop every process using the binary and confirm no updater is running. Verify `<installed-path>.previous` is an owner-controlled regular executable in the same protected directory. Copy it to a newly created owner-only staging file in that directory, run the staging file's `version` command, then atomically rename the staging file over the current executable and re-run `version` before restarting services. Do not perform this recovery on package-managed paths or use privilege elevation to bypass a refusal. See [Local CLI self-update policy](self-update.md) for the detailed trust, transaction, and recovery behavior.

## First-Release Tool Surface

- STDIO mode registers read-only lookup/download tools, prompt checklists, write workflow tools, attachment/image tools, and the read-only `health_version` tool.
- HTTP development mode from the CLI registers read-only tools and `health_version`. Production HTTP mode registers the full tool surface only behind OAuth authorization mode; every scoped call is checked against the tool's required scopes before the handler runs.
- The checked machine-readable source is `docs/tool-manifest.json`, generated with `go generate ./internal/tools`.
- Use `docs/tool-reference.md` for field-level contracts, mutation classes, upload sources, required scopes, MCP annotations, and clarification retry fields.

## Check InvenTree Instance Info

Call `get_inventree_instance_info` (no input) to confirm which InvenTree server/API version and instance identity a session is talking to, and to check the small operator-approved set of module/workflow-availability settings before assuming a feature (return orders, transfer orders, stocktake, project codes, part revisions/locking, barcode/label/report support) is usable.

- Returns `server`, `version`, `api_version`, `instance`, `plugins_enabled`, and, when the credential has sufficient privilege, `commit_hash`/`commit_date`/`up_to_date`.
- Returns `global_settings` and `user_settings` maps containing only the F-S71 operator-approved allowlisted keys (see `docs/api-schema.md` for the exact list and rationale); it never enumerates or exposes the full settings surface.
- A missing/renamed allowlisted key, or a credential without sufficient InvenTree staff access for `/api/settings/global/{key}/`, is omitted from the corresponding map and listed by key in `omitted_global_settings`/`omitted_user_settings` instead of failing the call -- do not treat a nonempty `omitted_*` list as an error.
- Requires only `inventree.read`; no `confirm` or destructive scope is involved.

## MCP Functionality-Gap Guidance

Current `server/discover` and legacy `initialize` publish the same advisory server instructions in STDIO and HTTP modes. They ask consuming agents to distinguish a missing `inventree-mcp` capability from input, authorization, configuration, or upstream limitations; explain any safe workaround; check open and closed project issues when GitHub access is available; and obtain operator approval before creating an untracked issue. Clients may ignore this guidance, and agents without GitHub access must disclose that they cannot verify existing coverage and ask whether the operator wants the gap checked and, if untracked, an issue created.

## ChatGPT Connector OAuth Setup

Production HTTP includes protected-resource and authorization-server metadata, an operator-facing setup page, CIMD `private_key_jwt` client authentication, PKCE S256 authorization-code exchange, refresh, encrypted MCP token envelopes, request-scoped credential recovery, and per-tool scope guards. The implementation follows the current [OpenAI authentication guide](https://developers.openai.com/plugins/build/auth) and does not allow an unsigned `none` downgrade.

- Required inputs: public connector URL, configured canonical HTTPS issuer/resource URLs, an allowed ChatGPT client metadata URL advertising the exact callback and same-origin JWKS, and an InvenTree Token or Bearer credential supplied only on the setup form.
- Preferred flow: ChatGPT discovers OAuth metadata; the server validates the CIMD document and PKCE request; the operator submits an InvenTree credential; the server validates `/api/user/me/`, creates a uniquely named dedicated connector token through `/api/user/me/token/` without rotating the submitted or earlier connector token, and returns a one-time code; ChatGPT authenticates the token exchange with a signed `private_key_jwt` assertion; the server issues encrypted access and refresh envelopes.
- Fallback: if dedicated-token creation is unavailable, the page discards the submitted secret and requires the operator to re-enter it plus explicitly select `Use this supplied credential`. The explicit `Cancel` action returns `access_denied` without using the credential. No authorization code is issued before that choice.
- Security boundary: MCP scopes restrict which handlers may run, but they do not reduce the upstream permissions carried by the sealed InvenTree credential. Setup state and CSRF cookies are short-lived and one-time; client assertion IDs are replay-protected within one running process, so restart or multi-replica replay protection requires external shared state; credential bodies are excluded from the MCP traffic log; browser responses use no-store, no-referrer, frame denial, and restrictive CSP headers. The HTTP server bounds request-body reads to 30 seconds and credential validation/token creation to 15 seconds.
- Dedicated-token cleanup: every successful creation uses a random setup-specific name so existing API keys and connector sessions are not rotated. If setup is abandoned after creation, code exchange never completes, or an authorization is no longer needed, revoke the unused `inventree-mcp-chatgpt-*` token in InvenTree. The database-free MCP server does not retain token IDs for automatic cleanup.
- Expected output: connector authorization success with `credential_source` set to `dedicated_token` or `supplied_token`, without returning the upstream credential.

## STDIO Setup

- Required inputs: `INVENTREE_URL`, `INVENTREE_TOKEN`, optional browser-facing `INVENTREE_WEB_URL`, optional `INVENTREE_AUTH_SCHEME`, `INVENTREE_UPLOAD_ALLOW_ROOTS`, `INVENTREE_UPLOAD_MAX_BYTES`, and optional `INVENTREE_MCP_DEBUG_TRAFFIC_LOG`.
- Preferred flow: validate configuration, seed logging context, run `inventree-mcp serve --transport stdio`, perform a read-only smoke test.
- Local upload flow: configure trusted operator-controlled upload roots with `INVENTREE_UPLOAD_ALLOW_ROOTS` or repeated `--upload-allow-root`; tune the byte limit with `INVENTREE_UPLOAD_MAX_BYTES` or `--upload-max-bytes` when the default limit is too small.
- MCP protocol flow: current clients use MCP `2026-07-28` discovery. Legacy initialization remains supported.
- Link flow: set `INVENTREE_WEB_URL` or `--inventree-web-url` to the exact frontend mount when users browse InvenTree through a different public authority, path prefix, or custom InvenTree basename; a stock deployment normally uses `https://inventory.example.test/web`. When omitted, links preserve the `INVENTREE_URL` site prefix and add InvenTree's stock `/web` frontend mount. Production requires HTTPS; both explicit and fallback bases reject credentials, queries, fragments, unsupported schemes, invalid authorities, and unsafe paths. Request/proxy data and OAuth envelopes never select the link authority.
- Debug traffic flow: set `--debug-traffic-log /secure/path/mcp-traffic.jsonl` or `INVENTREE_MCP_DEBUG_TRAFFIC_LOG` only while diagnosing MCP client behavior. The JSON Lines file records full MCP request and response payloads, including structured clarification results, tool arguments, and any sensitive data the MCP client sends. Valid returned `web_url` and `parent_web_url` values, including internal fallback authorities, may appear in this operator-enabled response capture.
- Clarify when: auth scheme is neither `Token` nor `Bearer`, URL is missing, upload allowlisted roots are not trusted, or TLS skip verify is requested outside local/test use.
- Expected output: STDIO MCP server ready for local clients.

## Reverse-Proxy HTTP Deployment

Production reverse-proxy HTTP deployment has configured canonical protected-resource and authorization-server metadata, bearer challenges, token audiences, setup/token endpoints, and OAuth-protected startup wiring. It supports path-preserving proxies with explicit trusted proxy CIDRs. Live packaged connector validation remains F-S10 work before this deployment is treated as operator-supported.

HTTP request bodies are bounded by `INVENTREE_MCP_MAX_REQUEST_BODY_BYTES` or `--mcp-max-request-body-bytes`, which defaults to 8 MiB. If the HTTP inline-upload limit is raised, raise this limit enough for base64 expansion plus JSON overhead; HTTP startup rejects inconsistent values. The setting does not constrain STDIO uploads. Keep the limit finite on untrusted HTTP endpoints.

Current HTTP clients use MCP `2026-07-28` sessionless POST requests, while legacy initialization remains supported. Client cancellation of a current-protocol POST propagates to the active tool handler; operators should treat cancellation as an unknown-result boundary for upstream writes unless the tool response or InvenTree read-back proves the outcome.

HTTP mode accepts the same debug traffic log option as STDIO. HTTP debug entries include request URIs including query strings, request bodies, response bodies, and streaming response chunks. In production, bearer authentication runs before full-body traffic capture, so unauthenticated request bodies are rejected without being written to the debug log. Authenticated request bodies and non-streaming responses are captured up to 1 MiB and use `body_truncated:true` when more data was forwarded; streaming response chunks are capped individually. Valid configured `web_url` and `parent_web_url` authorities and complete external-link query/fragment data can appear in authorized response bodies. Requests above the configured MCP request limit fail closed. Treat this file as sensitive and operator-local.

- Required inputs: internal listen address, `INVENTREE_URL`, optional public browser-facing `INVENTREE_WEB_URL`, public HTTPS issuer/resource URLs, exact public/internal MCP path, envelope keys, allowed client metadata URLs, trusted proxy CIDRs, and token lifetimes.
- Preferred flow: bind `INVENTREE_MCP_LISTEN` to loopback or a private service network; set `INVENTREE_MCP_PATH` to the exact path in `INVENTREE_MCP_OAUTH_RESOURCE_URL`; set `INVENTREE_MCP_TRUSTED_PROXY_CIDRS` to only the controlled proxy hops that can connect to the listener; and route the public path to the listener without stripping or rewriting its prefix. A same-host proxy normally uses `127.0.0.1/32,::1/128`; containers or private networks require the deployment's narrow actual proxy CIDRs.
- Forwarding policy: the configured issuer/resource URLs are authoritative. The server ignores `X-Forwarded-Host`, `X-Forwarded-Proto`, and `X-Forwarded-Prefix`. It accepts `X-Forwarded-For` only when the socket peer is trusted, walks the chain right-to-left through trusted hops, and uses the first untrusted address as the normalized source for per-IP limits and request-scoped logs. It never logs the raw forwarding header. Configure each trusted proxy to append its observed client address and prevent untrusted clients from connecting directly to the listener.
- Prefix example: issuer `https://mcp.example.test/connectors/inventree`, resource `https://mcp.example.test/connectors/inventree/mcp`, and `INVENTREE_MCP_PATH=/connectors/inventree/mcp` require the proxy to preserve `/connectors/inventree` on metadata, authorization, token, setup, and MCP requests. Prefix stripping and `X-Forwarded-Prefix` reconstruction are unsupported.
- Verify through the proxy: fetch `/.well-known/oauth-protected-resource<resource-path>` and `/.well-known/oauth-authorization-server<issuer-path>`, check their issuer/resource/endpoints against configured public URLs, then confirm the MCP resource returns a bearer challenge containing the canonical protected-resource metadata URL. Internal listener names, ports, and forwarding-header values must not appear.
- Troubleshooting: a startup error that the resource path does not match the HTTP path indicates a prefix mismatch; a prefixed public route returning `404` usually means the proxy stripped or rewrote the path; every request sharing the proxy IP for rate limits/logs means the peer CIDR is absent or the forwarding chain is malformed; unexpected public metadata must be corrected in explicit OAuth configuration rather than forwarded headers.
- Clarify when: the proxy cannot preserve paths, the trusted hop CIDRs are dynamic or unknown, the listener is reachable by untrusted clients, production config enables TLS skip verify, the requested client ID is not an HTTPS CIMD URL, or the document does not advertise `private_key_jwt` and a same-origin JWKS.
- Expected output now: HTTP MCP endpoint with connector setup, configured canonical OAuth metadata, signed-client token exchange, trusted source-IP resolution, and no MCP dispatch without a valid encrypted access-token envelope. Live packaged connector validation remains F-S10 work.

### OAuth Envelope Key Lifecycle

- Generate each 32-byte key with a cryptographically secure generator, for example `openssl rand -base64 32`, and assign a non-secret unique key ID. Store the resulting `INVENTREE_MCP_OAUTH_KEYS` value only in protected process environment or `/etc/inventree-mcp/inventree-mcp.env`, which packaged installs create with mode `0600`; never pass key material on the command line, commit it, or write it to the debug traffic log.
- Keep exactly one key in `active` state. To rotate normally, add a new active key and change the former active key to `decrypt_only`, restart, and retain the old key only for the bounded grace period needed by outstanding envelopes—never longer than the configured absolute session lifetime. Remove it after that grace period and restart again.
- If an envelope key may be compromised, remove it immediately instead of granting a grace period, install a new active key, restart the service, and require connector reauthorization because outstanding envelopes using the removed key become invalid. Rotate the sealed upstream InvenTree credentials as well if they may have been exposed.
- A startup failure about missing, duplicate, weak, or state-invalid keys is fail-closed. Correct the protected configuration rather than weakening validation.

## Packaged Systemd Deployment

- Required inputs: release package for the target Linux distribution, private HTTP listen address, path-preserving public reverse-proxy route, `INVENTREE_URL`, optional public browser-facing `INVENTREE_WEB_URL`, OAuth issuer/resource URLs, trusted proxy CIDRs, envelope keys, allowed client IDs, and token lifetimes.
- Preferred flow: install the `deb`, `rpm`, or `apk` artifact from the GitHub release, edit `/etc/inventree-mcp/inventree-mcp.env`, and keep `INVENTREE_MCP_LISTEN` bound to loopback or a private service network. Do not enable the service for live connector use until F-S10 is complete; during that validation, enable it only after canonical reverse-proxy routing has been verified. The unit waits for native readiness after runtime checks and listener binding, then expects watchdog heartbeats every half of its configured 30-second timeout.
- Clarify when: the operator expects STDIO mode from the packaged service, wants to expose the Go listener directly to the internet, has not validated canonical proxy routing, or expects Alpine/OpenRC service management from the `apk` package.
- Expected output: installed package files now, and a systemd-managed `inventree-mcp serve --transport http` process behind the deployment's validated path-preserving reverse proxy once F-S10 packaged live deployment validation is complete. After the managed HTTP lifecycle starts, `systemctl status inventree-mcp.service` reports sanitized startup, ready, degraded, stopping, or fatal text. Earlier configuration or logger initialization failures exit non-zero and are visible through ordinary systemd status/journal and restart handling. A missed heartbeat does not make the process self-exit: the server stops heartbeats, continues serving, and systemd terminates it when the watchdog expires before restarting it under `Restart=on-failure`. Development-only smoke tests can still run the binary directly with `--environment development --dev-incomplete-oauth` and expect only the skeleton MCP server plus read-only health/version tool; outside systemd, notification and watchdog behavior is a no-op.

## Maintainer Release

- Required inputs: clean `main`, selected semantic version tag `vX.X.X`, passing local validation, and GitHub Actions permissions that allow `contents: write`.
- Preferred flow: run `GOFLAGS=-trimpath go test -race ./...`, run `goreleaser check` and `goreleaser release --snapshot --clean` when the CLI is installed, confirm the `Release Preview` workflow passed on the release PR, create and push the `vX.X.X` tag, watch the GitHub `Release` workflow, then verify the GitHub release assets and `checksums.txt`.
- Clarify when: the version number is unclear, the tag already exists, GitHub Actions or `GITHUB_TOKEN` release permissions are disabled, snapshot package validation has not passed, or the release should include signing, SBOMs, containers, Homebrew, OpenRC packaging, or package repositories beyond GitHub release assets.
- Expected output: GitHub release containing Linux/macOS/Windows binary archives, Linux `deb`/`rpm`/`apk` packages, and checksums.

## Add Or Update A Purchasable Part

- Required inputs: part name or IPN/SKU, category or category ID, units where required, supplier/manufacturer details when available.
- Preferred lookup order: use `search_parts` for concise selection, then `get_part` for the complete approved scalar record before changing it; search categories, companies, and supplier/manufacturer part records, then create or update only the missing pieces.
- Clarify when: part/category/company matches are ambiguous, an existing part may already represent the requested item, or supplier/manufacturer identifiers conflict.
- Tool sequence: use `upsert_part_with_supplier_and_manufacturer` with `dry_run:true` first when the operator wants one safer workflow-level plan, then retry without `dry_run` after reviewing the plan. Use lower-level searches, stable-ID `get_company`/`get_supplier_part`/`get_manufacturer_part`, and the matching create/update tools when the operator needs step-by-step control.
- Optional MPN: omit it when unknown. Null, blank, and whitespace-only input is treated as omitted; the tools never invent a fallback manufacturer part number. The combined workflow searches the exact part and manufacturer pair first: it reuses one existing link, asks for clarification when multiple links match, or records `skip_manufacturer_part` when none exists. A direct `create_manufacturer_part` call performs the same duplicate search before the pinned server can reject an omitted MPN.
- Scalar part maintenance: lower-level `create_part` and `update_part` support consumable/template/lock/salable/testable flags, default expiry, keywords, a complete credential-free HTTP(S) external link, minimum/maximum stock, revision text, and Markdown notes. Use `clear_keywords`, `clear_link`, `clear_revision`, or `clear_notes` to write null; do not combine a clear flag with its replacement field. `default_expiry:0` resets the default and `maximum_stock:0` disables the maximum. Values must be finite and non-negative, and a nonzero effective maximum cannot be below the effective minimum. `creation_user` is exact-read-only; primary images remain in the dedicated image tools.
- Exact-read boundary: `get_part` preserves nullable computed quantities as null and returns creation, pricing, stock, allocation, `revision_of`, `revision_count`, and `variant_of` context as a factual snapshot. Nested category/default-location detail, category path, parameters, tags, price breaks, ownership, and barcode hash are not silently embedded; use their dedicated lookups or later approved stories.
- Family topology: use only `update_part_family_relationships` to assign, replace, or clear revision and variant targets. A revision must already have a nonblank revision code, cannot target a template, and must share the same variant template as its revision target; a variant must target a template. Pinned InvenTree 1.5.0 accepts the tested circular `revision_of` chain, so the MCP supplies the required bounded cycle guard; the MCP also rejects direct self-reference as an explicit safety policy. Supply stable target IDs or explicit clear flags, run `dry_run:true`, review both current references, requested targets, eligibility state, and bounded traversal evidence, then execute once with `confirm:true` and the returned `plan_hash`. Any self-reference, cycle, target/read failure, topology change, traversal-budget exhaustion, expired/reused token, or no-op is refused before PATCH. The tool conservatively requires read/write/operational/destructive OAuth scopes for every call because MCP security metadata is descriptor-level. Treat topology as single-writer state and never blindly retry a `partial_failure`; call `get_part` for the stable subject ID first.
- Expected output: `status`, ordered `actions`, field-level dry-run `planned_changes`, stable selected or created part, supplier, manufacturer, supplier-part, and manufacturer-part records when available, plus `omitted_recommended_fields` for missing recommended values. Review every planned field, including explicit false or empty values. Each `depends_on` entry maps an unresolved foreign-key `field` to the earlier planned create `action` that supplies it; factual record fields never use zero-ID placeholders. `planned_changes` is an advisory preview, not a confirmation token: execution repeats preflight and may return a different result after intervening upstream changes, so review again after any change or clarification. If a required stable ID, currency, supported company role, SKU, or duplicate decision is missing, the tool returns structured clarification. Definite validation rejection uses `validation_failed`; if an earlier write was applied or the result is ambiguous, `partial_failure` preserves completed `actions`, stable records, `remaining_actions`, safe validation fields when available, and a concrete `recovery_plan`.
- HTTP note: `create_part` and `update_part` require both `inventree.read` and `inventree.write` because duplicate/current-state preflight and exact read-back disclose part records. Other write tools use the scopes documented in the tool reference.

## Delete An Ordinary Part

- Use this to remove a part that was created by mistake and has no real usage history — for example, a non-stock purchase intended as a `create_purchase_order_extra_line` that was instead created as an ordinary inventory part. It is not a bulk or search-and-delete tool: it takes an exact stable part ID and refuses if the part is genuinely in use anywhere.
- Required inputs: the stable part primary key returned by `search_parts` or `get_part`.
- Tool sequence: call `delete_part` with `id` and no `confirm` to review the current part, its category, supplier parts, manufacturer parts, parameters, attachments, and related-part links; then retry with `confirm:true` to delete.
- Safety behavior: pinned InvenTree 1.5.0 only enforces two conditions of its own — a part must be deactivated (`active:false`, via `update_part`) before it can be deleted at all, and a part currently used as a component in another part's BOM is protected outright. Every other relationship is silently permitted by InvenTree once the part is inactive, and the consequences differ by relation: deleting a part with existing stock also destroys that stock item, while a referencing purchase-order line survives, orphaned. `delete_part` therefore refuses on its own, before ever calling the upstream endpoint, whenever the part is still active, or whenever stock, its own BOM, a build, a purchase-order line, a sales-order line, a variant part, a supplier part, a manufacturer part, a parameter, an attachment, or a related-part link references it — reporting every blocking record's stable ID so it can be reviewed and removed explicitly. Deactivate the part with `update_part`; use `delete_part_parameter`, `delete_attachment`, or the confirmed `delete_part_relation` plan to clear those supported blockers. Supplier-part and manufacturer-part deletion still require the InvenTree UI.
- Expected output: `status:"clarification_required"` with the previewed part and full dependency detail before confirmation, or with a `blocking` object naming every referencing category and its stable IDs when refused. After a confirmed deletion attempt, one of four outcomes: `status:"ok"`, `verified:true`, `recovered` omitted (false) for an ordinary clean deletion; `status:"ok"`, `verified:true`, `recovered:true` when the delete call itself returned an ambiguous error (a lost/dropped response, distinct from a definite upstream rejection such as a real 4xx) but read-back proves the part was deleted anyway; `status:"partial_failure"` with `record` and a recovery plan when read-back finds the part still exists; or `status:"partial_failure"` when the read-back itself cannot prove either outcome. `recovered:true` is informational, not a warning — treat it the same as an ordinary success, but be aware the mutation call's own response was unreliable. Requires `inventree.destructive` scope.

## Administer Related-Part Links

- Resolve a stable part ID, then use `list_part_relations` to see every link where it appears on either side; use `get_part_relation` for one stable relation ID. Endpoint order is preserved in records but is not semantic: pinned InvenTree rejects the same pair in reverse.
- `create_part_relation` takes two distinct stable part IDs and an optional note. It scans both endpoint directions under one bounded budget and refuses an existing unordered pair. Never reverse endpoints to work around a duplicate.
- `update_part_relation` changes only the note. Supply either `note` or `clear_note:true`, review the exact before/after preview, then repeat with `confirm:true` and its principal-bound `plan_hash`. The fresh confirmation read invalidates changes it observes, but there is no compare-and-swap between that read and PATCH; serialize UI, API, and MCP writers. Endpoint replacement is deliberately non-atomic: preserve the old endpoints and note, verify deletion before creating the new pair, and reconcile both directions after any ambiguous create. A failed create can leave no link; inspect current state before deliberately creating the replacement or restoring the old relation.
- `delete_part_relation` first returns the exact endpoints, note, and a five-minute single-use `plan_hash`; repeat with `confirm:true` and that token. Relation state changed before the confirmation read invalidates the plan, but another writer in the following DELETE gap is not preventable upstream. Verified absence returns `verified:true`; a `partial_failure` must be reconciled by exact relation ID before retrying.

## Administer Companies And Sourcing Links

- Required inputs: a stable company, supplier-part, or manufacturer-part ID. Resolve proposed part and company references before a sourcing-link update.
- Company boundary: `update_company` supports name, description, website, currency, active state, supplier/manufacturer/customer-addition roles, phone, nullable email, contact, tax ID, external `link`, and notes. It never accepts tag or image mutation; company primary images remain a separate `set_company_image`/`set_company_image_from_url`/`clear_company_image` workflow. `get_company` exact reads show all of the above plus the redacted primary-image URL and supplied/manufactured part counts; minimal recovery/error projections omit notes, phone, email, contact, and tax ID.
- Role changes: adding a supplier, manufacturer, or customer role is an ordinary guarded PATCH through `update_company` (`is_supplier`/`is_manufacturer`/`is_customer` set to `true`). Removing a supplier/manufacturer role requires `confirm:true` on `update_company` and is refused while any corresponding sourcing link exists within the bounded 1,000-row dependency preflight. `update_company` always rejects an explicit `is_customer:false` — removing the customer role requires the separate guarded `remove_company_customer_role` tool below.
- Nullable and clearable fields: `phone`, `contact`, `tax_id`, and `link` are plain (non-nullable) InvenTree fields, so send an explicit empty string to clear them, the same convention `website` already uses. `email` is genuinely nullable; use `clear_email:true` to write null. A replacement value and its clear flag are mutually exclusive where a clear flag exists.
- Duplicate identity: supplier-part identity is the trimmed case-insensitive `(supplier_id, sku)` pair; manufacturer-part identity is `(manufacturer_id, mpn)`. Searches and update preflight load one bounded upstream snapshot of at most 1,000 matching records, sort that snapshot by stable ID, and fail closed when completeness cannot be proved. Updates repeat the normalized duplicate check after PATCH; a collision or incomplete postflight becomes `partial_failure` even when the requested field values were applied.
- Exact detail: keep searches concise, then call `get_supplier_part` or `get_manufacturer_part` for the complete approved sourcing-link record. Supplier detail distinguishes the 100-character short `note` from long Markdown `notes` and includes read-time derived MPN, in-stock/on-order quantities, availability timestamps, and updated time. Manufacturer detail includes long Markdown notes and the manufacturer stable ID; use `get_company` separately for company detail. Derived MPN and stock values can change independently and are context, not identity.
- Nullable and availability writes: use the field-specific `clear_*` flag to write null. A replacement value and its clear flag are mutually exclusive. `notes` / `clear_notes` maintain long Markdown notes independently of supplier `note` / `clear_note`. Supplier `available` accepts a finite quantity and preserves explicit zero; availability timestamps, in-stock, and on-order values are read-only.
- Scope boundary: embedded part/company/manufacturer-link detail stays in exact lookup tools. Parameters, tags, and price breaks stay in their dedicated workflows; raw barcode hashes and write-only duplication commands are not exposed by ordinary sourcing tools.
- Direct-create recovery: when exact read-back fails after sourcing creation, `record` is omitted. Use the positive stable ID in `recovery` with `get_supplier_part` or `get_manufacturer_part`; if no usable ID was returned, perform the bounded identity search named in `recovery_plan` before retrying.
- Recovery and privacy: successful PATCH calls are read back by stable ID. Ambiguous response loss is recovered only when the read-back exactly matches every requested field, including null versus empty. A recovered success returns the full verified `record`, including a complete valid external URL, and retains the minimal URL-free `current` projection for compatibility; partial recovery, duplicate conflicts, and manufacturer base-part conflicts return only minimal `current`, `candidates`, or `blocking_supplier_parts` plus read-before-retry guidance. Otherwise inspect the named stable ID before retrying. Successful exact reads and verified writes preserve complete valid HTTP(S) external URLs, including query and fragment; userinfo/credentials are invalid. Errors, clarification candidates, and minimal recovery projections never include external links; recovery/error projections also omit descriptions, notes, contact, tax, raw upstream messages, and bodies.
- Concurrency: role/reference/duplicate preflight, PATCH, and postflight are separate upstream REST requests. Postflight repeats applicable company-role dependencies, supplier/manufacturer roles, base-part relationships, manufacturer-part associations, and normalized duplicate checks, but detection cannot make the update transactional or roll back a PATCH that raced. Serialize company and sourcing-link administration; if `partial_failure` reports a post-write integrity problem, inspect `current`, `candidates`, and `blocking_supplier_parts` before another write.
- HTTP note: exact reads require `inventree.read`; company/sourcing-link creation, the combined part workflow, and all three update tools require both `inventree.read` and `inventree.write` because their preflight or exact post-write read-back can disclose existing records.

- Model-type vocabulary: parameter templates use the parameter endpoint's qualified `app.model` values, for example `part.part` and `order.purchaseorder`. These are a different upstream enum from attachment model types; do not shorten them to `part` or `purchaseorder`.

- Merge: call `merge_parameter_templates` with distinct stable source/target IDs and `dry_run:true`. Optionally provide an exact `value_map`; all unmapped values remain unchanged. Review every planned/skipped row, category-link ID, and residual decision, then submit the unchanged inputs with `confirm:true` and the returned `plan_hash`.

Non-part rows are reported with their actual `model_type` and `model_id`. Category-default references include both link and category IDs; use the category-default tools below to remove or migrate them, then obtain a fresh merge plan. Non-conflicting part rows can still move, but the source template is deleted only after a fresh read proves it has zero rows and zero category links.

If merge returns `partial_failure`, do not replay the old confirmation: inspect every applied/failed action and current source/target row, discard the old hash, fix any manual decision, and run `dry_run:true` again. ## Change A Parameter Template's Uniqueness Policy

- When to use: an existing template needs its uniqueness enforcement tightened or relaxed (`0` none, `1` unique per model type, `2` globally unique) after it already has linked values. Setting `unique` at creation time uses `create_parameter_template`'s own `unique` field instead — this workflow is only for changing an *existing* template.
- Preview: call `update_parameter_template_uniqueness` with `template_id`, the target `unique`, and `dry_run:true`. Execution re-scans every linked row and refuses again if any conflict has reappeared since the preview, even if the token would otherwise match; a stale/expired/reused/wrong-principal token is also rejected. On success the template's exact `unique` is read back and verified.
- This tool never creates, deletes, or overwrites a parameter value itself — it only patches the template's `unique` field — so it publishes `destructiveHint:false` and requires `inventree.operational` rather than `inventree.destructive`.
- HTTP note: requires `inventree.read`, `inventree.write`, and `inventree.operational`.

## Create Purchase Order From Order Page

- Required inputs: stable supplier ID, a stable supplier reference or external order identifier, and at least one validated receivable line with a supplier-part ID and quantity. Optional non-receivable `extra_lines` preserve supplier invoice, surcharge, discount, product-link, or other context. Signed unit prices include zero and negative values; currency is required whenever either normal or extra-line unit price is supplied.
- Preferred lookup order: search supplier, search categories and parts for missing catalog entries, search supplier/manufacturer links for duplicates, run purchase-line preview validation, use `search_purchase_orders` and `search_purchase_order_lines` for duplicate/recovery checks, then call `create_purchase_order_with_lines` with `dry_run:true` before execution.
- Clarify when: category, part, supplier part, manufacturer part, parameter template, image, or purchase-order identity is ambiguous. A missing MPN is not itself ambiguous; omit it and never invent one. `upsert_part_with_supplier_and_manufacturer` reuses one exact part/manufacturer link, clarifies multiple links, or records `skip_manufacturer_part` when none exists before continuing the supplier-part path. Do not call `create_manufacturer_part` unless an MPN is known: pinned InvenTree 1.5.0 rejects the otherwise schema-optional omitted value, and the tool reports that as safe `validation_failed` output.
- Expected output: dry-run action summaries plus field-level `planned_changes` for every order, normal line, and extra-line create or patch, including derived or supplied references, quantities, prices, currencies, dates, destinations, notes, links, and the client-controlled normal-line `auto_pricing:false` and `merge_items:false` safety fields. A line's `depends_on` maps its unresolved `order` field to the planned order create when that stable ID does not exist yet. This is an advisory preview rather than a confirmation token; execution reruns preflight and may differ after intervening upstream changes. On execution, normal receivable lines are processed before non-receivable extra lines. Expect a stable purchase-order ID, generated InvenTree reference, separate stable `lines` and `extra_lines`, refreshed server-calculated `total_price`, retry-recoverable create/update results, and structured partial-failure output retaining all accumulated IDs/actions plus a concrete recovery plan. The exact `(supplier_id, supplier_reference)` pair is the order retry identity; derived normal-line references use `<supplier_reference>-<one-based index>`, while each extra line uses its required operator-supplied reference. Existing unmentioned normal or extra lines are never deleted. If more than one order has the exact pair, the workflow asks which order to reuse. The MCP annotation remains `idempotentHint:false` because concurrent creators can race across non-atomic lookup/create boundaries.
- Extra-line boundary: purchase-order extra lines are never receivable and never create stock. Use `search_purchase_order_extra_lines` and `get_purchase_order_extra_line` for review/recovery; create and update with `dry_run:true` before execution. A zero-priced informational line does not change InvenTree's order total; negative unit prices represent discounts. `project_code` is out of scope. Successful reads, dry runs, verified writes, and issue plans preserve complete valid HTTP(S) product links, including query and fragment, so functional URL changes invalidate current-state hashes. Credentials/userinfo are rejected; clarification candidates and ambiguous/minimal recovery projections omit the URL entirely.
- Extra-line recovery and deletion: MCP-managed creation treats trimmed `(order_id, reference)` as unique. A response-loss retry recovers only one exact field match; conflicts or multiple matches return sanitized stable-ID candidates for inspection. A cross-order update returns both refreshed source and destination totals in `affected_purchase_orders`. Use `delete_purchase_order_extra_line` without confirmation to preview one stable record, then retry with `confirm:true`; deletion additionally requires `inventree.destructive` and succeeds only after a not-found read-back plus refreshed-order total read-back.
- Duplicate-line recovery: if existing lines already share one derived workflow reference, use the returned candidates with `update_purchase_order_line` to give one duplicate a unique reference, then retry the combined workflow. No order or line PATCH is performed before all existing-line conflicts pass preflight.
- After creation, keep placement and receipt separate: dry-run `issue_purchase_order`, review the current order, every returned receivable line, every returned non-receivable extra line, and the target `PLACED` status in `planned_changes`, then call it with `confirm_issue:true` and the exact returned `plan_hash` only when the order is ready to be placed with the supplier. The confirmation call re-reads and hashes current order, line, and extra-line state, so any metadata, identity, quantity, pricing, destination, date, note, or receipt change observed before placement requires a fresh dry run. InvenTree cannot atomically combine that final preflight with the placement request: coordinate a single writer while issuing, and inspect the current order and lines before retrying any ambiguous result.
- Receiving: call `receive_purchase_order_items` with `dry_run:true`, stable line IDs, schema-valid partial quantities no greater than each outstanding quantity, and item or global locations only when line destinations do not suffice. Review the resolved location and outstanding-before/after values, then submit the exact returned `plan_hash` with `confirm_receive:true`. A changed order or line state requires a new dry run. Omit `complete_order` to respect InvenTree's configured auto-completion behavior. Set `complete_order:true` only on a dry run whose receipt will leave every ordinary line fully received; review the returned `completion_lines`, then keep that same explicit intent with the matching hash during confirmation.
- Receiving creates new stock items through InvenTree's native PO receive endpoint. It rejects virtual-part lines, does not merge into or update existing stock, and never auto-issues a pending order.
- Omitted, empty, or whitespace-only receipt packaging uses the supplier-part packaging; provide a non-blank override to change the created stock item's packaging.
- If receipt execution returns `partial_failure`, do not retry blindly. Read every purchase-order line and call `search_stock_items` with the order's `purchase_order_id`; use the returned source-order fields to determine whether the first mutation succeeded, then prepare a new dry-run plan only for any confirmed remainder.
- If receipt returns stock items but reports a `complete_purchase_order` failure, the receipt succeeded. Preserve those stock IDs, do not repeat any receipt, read the order and all ordinary lines, then use a fresh `complete_purchase_order` dry run if it is still placed and fully received.
- Deferred completion: call `complete_purchase_order` with `dry_run:true` and the stable order ID, verify every returned ordinary line is fully received and `planned_changes` contains `status:30` plus `accept_incomplete:false`, then call it with `confirm_complete:true` and the exact hash. The tool does not permit incomplete completion. An already-complete order is a no-write success; an ambiguous result must be read back and is recovered only when the exact order is `COMPLETE`.
- Hold, resume, and cancel: use `search_purchase_orders` with `status:25` to find orders currently on hold. These three dedicated tools each dry-run with `dry_run:true` and a stable `order_id`, then execute with `confirm:true` and the exact returned `plan_hash`, which is an opaque, principal-bound, single-use, five-minute token rather than a stateless content hash — a token issued by one operator or connector session cannot be consumed by another, and it cannot be replayed. `hold_purchase_order` accepts a `PENDING` or `PLACED` order; an already-`ON_HOLD` order is a no-write `already_on_hold` success. Because InvenTree has no native transition back to `PENDING` and resuming always places the order with its supplier, holding a `PENDING` order returns a `warning` in the plan — review it before confirming. `resume_purchase_order` accepts only an `ON_HOLD` order and always results in `PLACED`; an already-`PLACED` order is a no-write `already_placed` success. `cancel_purchase_order` accepts `PENDING`, `ON_HOLD`, or `PLACED` orders and refuses a `COMPLETE` order or one where any ordinary line has received quantity greater than zero — resolve received stock first; an already-`CANCELLED` order is a no-write `already_cancelled` success. All three verify exact refreshed order status after mutation and return `partial_failure` with a fresh-dry-run recovery plan if that cannot be proven; none of them expose generic status editing, custom-status mutation, or whole-order deletion.
- Do not have multiple operators or integrations receive the same purchase-order line concurrently. InvenTree 1.5.0 serializes line updates but can still accept a previously prepared quantity after the outstanding amount changes; this narrow race is an accepted operational limitation.
- End-to-end recovery: after catalog and sourcing preflight, use the combined part workflow with `dry_run:true`, verify its stable outputs through the matching search/get tools, preview the purchase lines, and use the exact supplier reference for purchase-order dry run, execution, and recovery. On `validation_failed` or `partial_failure`, follow only the returned recovery plan and remaining actions; never replay already completed steps blindly.
- One-shot option: `create_purchase_order` may omit `supplier_reference`, in which case InvenTree still generates the internal reference. Use that lower-level tool only for intentional one-shot creation; recovery after a client or tool interruption is provided by `create_purchase_order_with_lines` and requires a stable supplier reference.
- Exact reads: `get_purchase_order` and `get_purchase_order_line` return the complete approved field set — issue/completion/update dates, line/completed counts, overdue, status text/custom key, supplier name, creator user ID, Markdown notes, and `link` on the order; SKU, MPN, IPN, internal part name, total price, discount, overdue, build-order ID, and effective `auto_pricing` on the line. `merge_items` is never returned by any read; it only affects the write that sent it. Nested order, part, supplier-part, and destination detail remain separate lookups (`get_purchase_order`, `get_part`, `get_supplier_part`, `get_stock_location`); a null total price on a line means InvenTree has not computed one, not zero.
- Ordinary metadata updates: use `update_purchase_order` for description, Markdown notes, `supplier_reference`, dates, currency, destination, and `link` by stable order ID, with `clear_notes`/`clear_start_date`/`clear_target_date`/`clear_destination` for explicit nulling. `creation_date` has no clear flag: pinned InvenTree 1.5.0 resets it to the current date rather than clearing it when sent null, so this tool only supports setting it, never clearing it. `link` also has no matching `clear_link` flag: the schema models it as string-or-empty rather than nullable, so send an explicit empty string to clear it, the same convention purchase-order extra lines already use. `update_purchase_order` never accepts the supplier company or the internal InvenTree `reference`; use the placement, receiving, and completion tools above for status changes. `update_purchase_order_line` similarly accepts `link` (cleared the same way, with an empty string) and `discount` alongside its existing fields, following the same credential-free HTTP(S) `link` policy as extra lines.

## Review And Apply A Stocktake Adjustment

- Required inputs: one stable stock-item ID, a nonblank audit reason, and exactly one intended operation: relative `delta`, absolute `observed_quantity`, target `status`, a target `delete_on_deplete` policy, complete intentional delete-on-deplete removal, or complete/partial transfer to one explicit stable destination-location ID.
- Preferred flow: fetch `stocktake_review`; call the selected tool with `dry_run:true`; review current and proposed quantity, location, status, batch, serial, packaging, `delete_on_deplete`, and any high-risk warning; then submit the returned opaque `plan_hash` token with `confirm:true` within five minutes from the same principal. The token is single-use; a newer dry run for the same action and item supersedes it, and a server restart invalidates it. If outstanding-plan capacity is reached, execute or wait for reviewed tokens to expire before preparing more plans.
- Clarify when: stock identity, current source location, explicit transfer destination, measured quantity, relative-versus-absolute intent, target status, or audit reason is missing or ambiguous. Never infer a transfer destination or combine a quantity-only stocktake with an implicit location, status, batch, serial, or packaging change.
- Tool selection: use `adjust_stock_quantity` for relative add/remove corrections, `stocktake_adjustment` for an absolute physical count, `set_stock_status` only for status, `set_stock_delete_on_deplete` only to change whether the item deletes itself at a future depletion, and `transfer_stock_item` for one safe item's complete current quantity or an explicit positive partial quantity to one destination. Quantity decreases and `Destroyed`, `Rejected`, or `Lost` transitions are high-risk. No-op changes are refused. Relative and absolute quantity changes are refused for serialized stock; change individual serialized items instead, while status-only changes remain supported. If `delete_on_deplete` is true, those non-destructive tools still refuse a target quantity of zero. Use `deplete_stock_item` only when the complete current positive quantity should be removed and the stock-item record intentionally deleted.
- Delete-on-deplete-policy flow: call `set_stock_delete_on_deplete` with `dry_run:true`; review the current and proposed `delete_on_deplete` boolean plus the same quantity/allocation/relationship context `deplete_stock_item` shows, since that context describes what would be lost if the record is later deleted. This tool never removes stock itself and works at any quantity including zero. Enabling (`true`) is high-risk because it authorizes InvenTree to delete the record the next time any depletion transaction — this MCP's `deplete_stock_item`, InvenTree's own UI, or a native API call — reduces its quantity to zero; disabling (`false`) is not high-risk because it only revokes that authorization. Execute only with the matching token and `confirm:true`; a request that already matches the current policy is refused as a no-op before a token is issued. **Pinned InvenTree 1.5.0's global `STOCK_DELETE_ON_DEPLETE` setting defaults to enabled**, and neither `create_stock_item` nor `create_initial_stock_entry` exposes this field, so newly created stock is already eligible for deletion at depletion unless this tool is used to disable it first.
- Delete-on-deplete flow: call `deplete_stock_item` with `dry_run:true`; review the exact quantity, location, status, allocation, serial, build/consumption, installation, parent/child, supplier, and order context plus `will_delete:true`. The tool refuses unavailable, allocated, serialized, building, consumed, installed, parent-linked, or child-bearing stock. Supplier, purchase-order, and completed-build provenance remains visible but does not block removal by itself. Execute only with the matching token and `confirm:true`; success requires exact-ID absence verification, and `recovered:true` means a lost successful removal response was proven by that verification.
- Transfer flow: call `transfer_stock_item` with `dry_run:true`, one stable currently located source ID, an explicit stable destination ID, the audit reason, and omit `quantity` for a complete move or provide a positive quantity smaller than current stock for a split. Review source/destination paths, source remainder, destination quantity, safety, provenance, and `will_split`. The MCP accepts every exact-read destination and leaves structural, external, ownership, and other destination validity to InvenTree; it refuses same-location requests and unsafe source states. InvenTree's tracking count records audit history and is not a child-stock blocker. Execute only with the matching token and `confirm:true`. Complete success requires the original stable stock-item ID at the reviewed destination; split success requires the original ID at the reviewed source remainder plus exactly one distinct destination `split_record` with matching provenance. If a split result is ambiguous, `partial_failure` directs `get_stock_item` and `search_stock_items` reconciliation; never retry blindly.
- Expected output: a current-state-bound before/after plan during dry run and a refreshed stock item after non-destructive execution, or verified absence after intentional depletion. Do not allow another operator or integration to adjust the same stock item concurrently. Execution rejects state changes seen during preflight, but InvenTree provides no atomic conditional mutation for the narrow interval before the write. If state changes or execution returns `partial_failure`, do not retry blindly; use `get_stock_item` to inspect the stable ID before preparing a new plan.

The tool refuses an already-serialized item (use `set_stock_serial` instead), a non-trackable base part, and a serial already used by another stock item for the same part or, when the instance enables `SERIAL_NUMBER_GLOBALLY_UNIQUE`, any part. Execute only with the matching token and `confirm:true`.
- Replace-or-clear flow: call `set_stock_serial` with `dry_run:true`, the stock-item ID, and either a replacement `serial` or `clear_serial:true` (never both). Review the before/after serial and the high-risk warning — every change here rewrites stock identity and downstream audit context. The tool refuses an unserialized item (use `assign_stock_serial` instead) and a no-op replacement. Execute only with the matching token and `confirm:true`.
- Relationship safety: both `assign_stock_serial` and `set_stock_serial` share one guard that refuses allocated, building, consumed, installed, parent-linked, child-bearing, customer-assigned, or sales-order-linked stock — resolve those relationships (release the allocation, complete/cancel the build, uninstall, etc.) before either tool will plan a serial change.
- Expected output: a current-state-bound before/after plan during dry run and a refreshed stock item after execution. Serial identity may be referenced by labels, external systems, or history this MCP cannot see; verification proves InvenTree's own state, not downstream synchronization. If execution returns `partial_failure`, do not retry blindly; use `get_stock_item` to inspect the stable ID before preparing a new plan.

## Install Or Uninstall A Stock Item

- Required inputs: a stable parent stock-item ID and a stable child stock-item ID for install; a stable installed child stock-item ID and an explicit destination stock-location ID for uninstall; a nonblank audit reason for either.
- Tool selection: use `install_stock_item` to record that one available, quantity-1 stock item has been physically installed into another stock item's Bill of Materials; use `uninstall_stock_item` to record that a currently-installed child stock item has been physically removed to an explicit destination location. Neither tool splits or serializes stock — the child stock item must already have exactly quantity 1, and while InvenTree 1.5.1 does not itself require it to carry a serial number, most real installs involve a serialized item.
- Install flow: call `install_stock_item` with `dry_run:true`, distinct `parent_stock_item_id` and `child_stock_item_id`, and the reason (a stock item cannot be installed into itself). Review the plan's `install` context, including the confirmed Bill of Materials match and the child's safety snapshot. The tool refuses a child that is unavailable, already installed elsewhere, allocated, building, consumed, split-linked, customer-assigned, or sales-order-linked, and refuses a parent in an equivalent unsafe state — an already-nested parent (itself installed in something else) or a parent that already has other installed items is explicitly allowed. It also refuses a child part not in the parent part's Bill of Materials, and refuses any install that would create a cycle in the installed-in relationship. Execute only with the matching token and `confirm:true`; the refreshed child record shows `belongs_to` set to the parent and `location` cleared.
- Uninstall flow: call `uninstall_stock_item` with `dry_run:true`, the installed child's `stock_item_id`, an explicit `destination_location_id`, and the reason. InvenTree does not itself reject uninstalling an item that was never installed anywhere — it would silently accept the request and change the item's location — so this tool requires an existing `belongs_to` relationship before it will plan anything. The same allocation/building/consumption/customer/sales-order safety checks apply. Execute only with the matching token and `confirm:true`; the refreshed record shows `belongs_to` cleared and `location` set to the destination. Requires `inventree.destructive` because it removes an established, audited relationship.
- Expected output: a current-state-bound before/after plan for the affected item during dry run, `plan_hash`, and a refreshed exact-read record with `verified` (and `recovered` if the mutation response was ambiguous but read-back proved it) on execution. If execution returns `partial_failure`, do not retry blindly; use `get_stock_item` on the stable ID before preparing a new plan. Physical installation cannot itself be verified by the API — this workflow can only guard and confirm InvenTree's recorded relationship.
- Audit trail: InvenTree 1.5.1 records native stock-tracking history for both directions and both sides — the child gets an "Installed into assembly"/"Removed from assembly" entry and the parent gets an "Installed component item" entry — visible through `list_stock_tracking_entries`/`get_stock_tracking_entry`, independent of the plan's own `reason` field.

## Review Stock Tracking History And Historical Stocktakes

- Required inputs: one stable stock-item ID (`list_stock_tracking_entries`), a stable part ID (`list_stock_tracking_entries` or `list_part_stocktakes`), or one stable event/snapshot ID (`get_stock_tracking_entry`, `get_part_stocktake`).
- Preferred flow: call `list_stock_tracking_entries` with `stock_item_id` or `part_id` to review a bounded, complete snapshot of audit events sorted by stable event ID (not upstream `date`, which is not guaranteed unique or ordered across same-instant events); use the concise `label`, `tracking_type`, and redacted `deltas` to identify the event, then call `get_stock_tracking_entry` by its `pk` for the exact record including `notes`. Use `list_part_stocktakes` with `part_id` for historical snapshots (date, item count, quantity, min/max cost and currencies), then `get_part_stocktake` by `pk` for one exact snapshot.
- `deltas` is InvenTree's own per-event audit payload; its keys vary by `tracking_type` (for example `added`/`removed`/`quantity` for manual adjustments, `location` for a transfer, `old_status`/`status` for a status change). The MCP strips any nested `*_detail`/`created_by` full-record object InvenTree embeds in some event types (a transfer's `location_detail` and a purchase-order receipt's `purchaseorder_detail.created_by` were confirmed to leak nested location and user records, including an email address, during F-S46's pinned spike) and enforces bounded depth/key-count/byte-size limits on what remains, plus a content-based check that also strips a nested object carrying an `email`/`username`-shaped field under any other key name as defense-in-depth against an event type this spike did not observe. Treat `deltas` as informational context, not a stable typed contract, and never assume every key exists for every event.
- Nested item, part, and user detail on both tracking and stocktake reads are never embedded; use `get_stock_item`, `get_part`, and existing owner/user context separately.
- The history tools are entirely read-only: they never create, adjust, or delete stock, and never generate new stocktake entries or reports. Use `generate_stocktake` for the separate aggregate-generation workflow.
- **`list_part_stocktakes`/`get_part_stocktake` are unrelated to `stocktake_adjustment`** (see "Review And Apply A Stocktake Adjustment" above): `stocktake_adjustment` records an absolute quantity count against one stock item, which produces an ordinary `list_stock_tracking_entries` audit event (`tracking_type` "Stock counted"), not a `PartStocktake` snapshot. `list_part_stocktakes` reads InvenTree's separate periodic-report `PartStocktake` model, which this MCP never writes to.
- **Historical stocktakes are usually empty.** Pinned InvenTree 1.5.0's own `PartStocktake`-creation endpoint fails on every request (a confirmed upstream bug), and its generation endpoint only enqueues a background-worker job most deployments -- including this repository's own Testcontainers suite -- do not run. `list_part_stocktakes` returning `count:0` for a real part is expected and does not mean the tool is broken; a populated result requires an operator to have generated a snapshot through the InvenTree web UI (or a deployment that runs InvenTree's background worker) first.
- Clarify when: neither `stock_item_id` nor `part_id` is supplied to `list_stock_tracking_entries`, `part_id` is missing from `list_part_stocktakes`, or a filtered history exceeds the 1,000-record bounded scan (narrow the filter or paginate with `offset`/`limit`).
- Expected output: `status:"ok"` with `count`, bounded `results`, and no `clarification` on success; `status:"clarification_required"` with the missing/invalid filter on a bad request; `status:"not_found"` for an unknown exact ID. Pinned InvenTree source restricts `get_part_stocktake` to staff/admin accounts (this repository's test infrastructure only supports a staff/admin fixture account, so the exact non-staff behavior is documented from InvenTree's source rather than independently live-verified); a non-staff credential is expected to surface InvenTree's ordinary `403` rather than a special-cased MCP error.

## Generate A Guarded Stocktake

- Resolve exactly one stable `part_id`, `category_id`, or `location_id`. The selected part includes variants, the selected category includes subcategories, and the selected location includes sublocations per the upstream contract.
- Set `generate_entry:true`, `generate_report:true`, or both explicitly. Run `generate_stocktake` with `dry_run:true`, review the complete selector/flag plan, then confirm it with the returned single-use `plan_hash` and `confirm:true`.
- InvenTree accepts the request by enqueueing a background `DataOutput` task. `generate_stocktake` returns the sanitized task ID immediately with `status:"pending"`; call `poll_stocktake_generation` with that same `task_id` and an optional `wait_seconds` (capped at 30) until it returns `status:"ok"` or `status:"partial_failure"`. A pending response never starts another generation.
- A bounded poll may remain `pending`: in the pinned worker-backed characterization, a combined entry/report task stayed at `progress:0/1` with no output after 30 seconds. Use an overall wait budget of 90 seconds by default (three consecutive maximum 30-second polls); then stop and ask the operator. A caller may choose a shorter or explicitly approved longer budget, but must retain the same, same-principal task handle. Do not retry by generating a new task, and do not expect report content until the upstream task exposes an output artifact. Handles expire after 24 hours and are invalid after a server restart.
- When a completed task supplies a report URL, the poll tool validates that it resolves inside the configured InvenTree instance, rejects userinfo and redirects, applies the bounded download limit, and returns sanitized source metadata plus bounded content. It never follows an arbitrary external report URL.
- Permission and duplicate boundary: the pinned live stack returned HTTP 403 for a non-staff credential, while two identical same-day requests from the staff credential returned distinct task IDs. Treat the operation as staff-gated and non-idempotent; after a pending or failed poll, continue polling the same task before considering a new dry-run/confirmation. If enqueue returns an ambiguous transport/server failure, do not retry: reconcile InvenTree's task queue or stocktake history first because the original request may have been accepted.

## Administer Stock Locations And Metadata

- Required inputs: stable location, owner, location-type, or stock-item IDs for every referenced record; a nonblank location name for creation; and an explicit approved field set for updates.
- Preferred flow: fetch `stock_administration_checklist`; search locations and location types, and use `search_owners` plus `get_owner` before selecting a location's initial owner; use exact get tools; create or update ordinary location metadata after duplicate/reference preflight. For parent, structural, external, batch, expiry, packaging, notes, or link changes, run the applicable tool with `dry_run:true`, review the complete current-state plan, then send the exact `plan_hash` with `confirm:true`.
- Duplicate rule: trim surrounding name whitespace and compare case-insensitively under the exact parent. Roots and children are separate namespaces, and the same name under another parent is allowed. Completeness-sensitive scans stop and ask for operator direction above 1,000 records.
- Boundary: `update_stock_location` never changes parent, structural, external, or owner state; use `restructure_stock_location` under operational scope for parent/structural/external, and `assign_owner` (see below) to replace or clear the location's owner. `update_stock_item_metadata` never changes location, quantity, status, serial, ownership, supplier/source links, pricing, `delete_on_deplete`, installation, or order/build fields. No F-S21 tool deletes locations or stock items.
- Provenance correction: use `update_stock_item_provenance` only for an explicitly reviewed correction to an existing stock item's supplier part, purchase order, purchase price, or purchase-price currency. Start with `dry_run:true`, verify that the supplier part belongs to the stock item's base part and that a selected supplier part matches the selected purchase order's supplier, then confirm with the exact principal-bound, five-minute, single-use `plan_hash`. Replacement/clear operations require `inventree.read`, `inventree.write`, `inventree.operational`, and `inventree.destructive`; the tool is non-idempotent and reports `partial_failure` when exact read-back cannot prove the complete reviewed state. The native PATCH changes current provenance but does not create a stock-tracking event or rewrite historical tracking entries, so retain the reviewed correction context externally. The base part, quantity, location, status, serial, allocation, installation, build/consumption, customer, and sales provenance remain outside this tool. The pinned stock serializer does not permit clearing `purchase_price_currency` with null.
- Exact reads: `get_stock_item` returns the complete approved field set, including SKU, MPN, `expired`, `stale`, sales-order reference, and the root-to-leaf `location_path` alongside existing quantity, status, serial/batch/expiry/packaging, ownership, relationship, pricing, and source-order/build fields. SKU and MPN are null when the item has no linked supplier part (or that supplier part has no manufacturer-part link); sales-order reference is null until the item is allocated to a sales order (no sales-order tool exists; treat it as informational only). Nested location, part, and supplier-part detail remain separate lookups (`get_stock_location`, `get_part`, and the supplier-part lookup tools); `search_stock_items` keeps its concise projection and does not return these fields. All of these new fields are read-only; `update_stock_item_metadata`'s writable field set (batch, expiry date, packaging, notes, link) is unchanged.
- Recovery: after `partial_failure`, call `get_stock_location` or `get_stock_item` and inspect same-parent siblings where relevant. Prepare a fresh plan from current state; never retry an unknown write blindly.
- F-S67 effective icon: `get_stock_location` (and `search_stock_locations`) now returns InvenTree's computed effective `icon` alongside the configured, writable `custom_icon`. `custom_icon` takes precedence when set; otherwise the icon falls back to the location's `location_type`'s icon, and finally to none. Only `custom_icon` is writable through `create_stock_location`/`update_stock_location`; `icon` is read-only output.
- F-S67 location-type administration: `create_stock_location_type` and `update_stock_location_type` set `name`, `description`, and `icon` after a bounded case-insensitive duplicate-name preflight — InvenTree itself does not enforce name uniqueness on this endpoint, so this MCP-side check is the only protection. All three fields are non-nullable optional strings upstream; supply an explicit empty string to clear one, never a null/clear flag. `delete_stock_location_type` previews a principal-bound `plan_hash` that reports every referencing location's stable ID (`referencing_location_ids`) for review, then requires `confirm:true` plus that exact `plan_hash` to execute — deleting a referenced type is allowed and safely clears `location_type` (and the referencing locations' effective icon) on those locations rather than InvenTree refusing or cascading further, so review the reported locations before confirming if that matters for your workflow. Any change to the type or its references between preview and confirm makes the plan stale.
- F-S68 stock-location deletion: call `delete_stock_location` with the stable location `id` and no confirmation to obtain the exact current record, bounded dependency IDs, and a principal-bound `plan_hash`. Confirm only after the location is empty and unreferenced by stock items, child locations, part/category defaults, purchase orders or ordinary lines, builds, transfer orders, or location parameters. Retry with `confirm:true` and that exact token. Any dependency, incomplete scan, state drift, response-loss ambiguity, or read-back uncertainty fails closed; the tool never transfers stock, clears defaults or parameters, reparents children, cascades, or rewrites references. Requires read, write, operational, and destructive scopes.
